# メール送信機能 / 承認フロー通知メール テスト手順 (引き継ぎ)

最終更新: 2026-08-24 (担当交代時点)

対象は **メール送信機能** (`MailField` / `BulkMailField` / Gmail 経路 / 送信履歴) と
**承認フローの順番到達通知メール** (`ApprovalMemberContractField.TurnNotifyMail`)。
機能そのものの設計は `メール送信機能仕様.md` / `承認フロー機能仕様.md` を参照。ここには**テストのやり方と現状**だけ書く。

---

## 1. テスト環境は2つ (どちらもローカル・git 管理外)

アプリは**リポジトリの Example アプリ1つを共用**し、ASP.NET Core の環境プロファイルで切り替える
(アプリのコピーはしない = 常に今のソースで動く)。ポートが違うので**同時起動できる**。

| | メールテスト | 承認フローテスト |
|---|---|---|
| 起動プロファイル (VS) | `Extras.Server (MailTest)` | `Extras.Server (Approval)` |
| URL | https://localhost:7369 | https://localhost:7269 |
| 環境名 | `MailTest` | `Approval` |
| 設定ファイル | `Source/Example/.../Extras.Server/appsettings.MailTest.json` (git 管理外) | 同 `appsettings.Approval.json` (git 管理外) |
| 環境フォルダ | `C:\Codeer.LowCode.Blazor.Local\MailTest\` | `C:\Codeer.LowCode.Blazor.Local\ApprovalTest\` |
| DB | `MailTest\Data\mail_test.db` | `ApprovalTest\Data\approval_test.db` |
| デザイン | `MailTest\Design` → `MailTest\Designs\App.zip` | `ApprovalTest\Design` → `ApprovalTest\Designs\App.zip` |

各環境フォルダの `README.md` に**その環境固有の詳細チェックリスト**がある (この文書はその上位版)。

- ソリューション: `Source/Example/Extras/Extras.sln` を VS で開き、起動プロファイルを選んで実行
- デザイン編集: `Extras.Designer` を起動して各環境の `Design` フォルダを開く。
  編集したら **`Designs\App.zip` に固め直す** (これが反映の唯一の経路)。サーバー再起動は不要 (`UseHotReload: true`)
- `appsettings.*.json` を変えたときだけサーバー再起動が必要

### ★ 引き継ぎ先が別マシンの場合

環境フォルダ (`MailTest` / `ApprovalTest`) は**git に入っていない**ので、そのマシンで作り直す必要がある:

1. `Data` フォルダの `ddl.sql` から DB を作る (下記コマンド。ddl.sql も環境フォルダにあるので、
   引き継ぎ時はフォルダごとコピーするのが早い)
   ```
   python -c "import sqlite3;c=sqlite3.connect('mail_test.db');c.executescript(open('ddl.sql',encoding='utf-8').read());c.commit()"
   ```
2. `Design` を zip して `Designs\App.zip` に置く (デザイナのデプロイでも可)
3. Gmail の鍵を置く (次節)
4. `appsettings.MailTest.json` / `appsettings.Approval.json` のパスを自分の環境に合わせる (どちらも git 管理外。`appsettings.Development.json` は通常開発用でメール設定を持たない)

## 2. Gmail (実送信) の準備

**ユーザー同意モード** (管理者権限不要) を使っている。鍵は `MailTest\Secrets\` に置き、
**承認テスト環境からも同じファイルを絶対パスで参照**している (複製を増やさないため。
`MailTest` を消すと承認通知も送れなくなる)。

1. OAuth クライアントの JSON を `MailTest\Secrets\client_secret.json` として置く
2. `MailTest\Tools\get_gmail_token.py` を実行 → ブラウザで送信アカウントにログインして許可
3. `MailTest\Secrets\token.json` が生成されれば完了

- ★ **GCP の OAuth 同意画面が「テスト中」ステータスだとリフレッシュトークンが7日で失効する**。
  「送れていたのに急に `invalid_grant`」はまずこれ。同意画面を本番公開 or 内部アプリにするか、トークンを取り直す
- 呼び名の既定は appsettings の `Mail.DefaultInfraName` / `DefaultBulkInfraName` = `"Gmail"`。
  **ここが空だと送信は「呼び名未指定」エラー** (テンプレの対応表 `MailSenderTable` は空を引き受けない)
- ユーザー単位トークン (`GmailTokenField`) は 2026-08-28 に撤去。差出人は常にシステム送信者 (TokenSecret)

### ★ 誤送信防止の設計 (崩さないこと)

1. **両環境の DB のアドレスはすべて自分のアドレスのプラスアドレス** (`自分のアドレス+タグ` の形。Gmail の
   プラスアドレスは自分の受信箱に届く)。承認フローは**順番が回るたびに自動送信**されるので、
   実在の他人のアドレスを DB に入れない。実際の値は各環境フォルダの `README.md` と DB を見ること
   (この文書にはアドレスを書かない)
2. `MaxBulkCount: 20` — 一斉送信は20件超で強制エラー (黙って切り詰めない)
3. 差出人はアドレス指定不可 (システム or ログインユーザー本人のみ = なりすまし構造排除)
4. `DebugRedirectAllTo` (全メール横取り) は両環境で `""`。本番DBコピー環境向けの機能

## 3. メールテスト環境 (7369) の内容

画面: 受注 (単発メール) / メール配信 (一斉) / 宛先名簿 / ユーザー / メール送信履歴。
詳細な期待値は `MailTest\README.md` の表 (1-1 〜 1-17、Phase 2、異常系) を使う。要点だけ:

| 観点 | 確認すること |
|---|---|
| 単発送信 | 受注画面の `MailField` ボタンで送信。To/Cc/Bcc/返信先が入力どおり。件名・本文の `{変数}` 解決 (リンクパス・書式適用・`{{}}` リテラル) |
| 値優先 | スクリプトで設定した値が変数より優先される (`FormMail.To = ...`)。テキスト添付も同経路 |
| 差出人 | 常に送信インフラ設定のシステム送信者。クライアントが載せた From は破棄される |
| HTML本文 | `IsBodyHtml` ON で HTML として届く。一斉送信では変数値が HTML エスケープされる |
| 一斉送信 | メール配信 → 一斉送信。**配信停止 (OptOut) とアドレス空はスキップ**。記録は送信履歴モジュール + 送信明細 (1 宛先 1 行・解決後の本文)。サマリ列は廃止 |
| 送信履歴 | 送信操作1回につき1行 (`MailInfraName` / `Subject` / `Total` / `Success` / `FailureDetails` / `SourceModule` / `SourceId`)。画面からは誰も書けない |
| ユーザートークン | 壊れた値を登録 → `invalid_grant` で失敗する = 差出人のトークンが使われた証明。登録解除でシステムトークンにフォールバック |
| 異常系 | 鍵のパスを壊す / 知らない呼び名を設定 / 21件以上の一斉送信 / 未保存で一斉送信 |

## 4. 承認フローテスト環境 (7269) の内容

画面: 経費申請 / 購買申請 / 承認待ち (自分が今待たれている行だけ) / 承認状況 (全フロー。状態(複数)・申請者・経路で検索。現在担当者列で誰で止まっているかが分かる) / 承認経路マスタ / ユーザー / メール送信履歴。
承認待ち・承認状況は QueryField の検索用モジュール (MyApprovalList / ApprovalStatusList)。承認フロー側のモジュール (ApprovalFlow / Member / History) は UI を持たない。
詳細は `ApprovalTest\README.md` (Phase 1〜3)。要点:

- **購買申請** = 経路マスタから金額で経路を選ぶ構成。スクリプト `OnBuildRoute` が 10万円未満は「購買ルート」(一次のみ)、
  10万円以上は「購買ルート(高額)」(一次 + 二次) を読む (金額0以下・申請者自身が承認者に含まれる → **申請中止・保存もされない**)
- **経費申請** = 経路マスタの「経費ルート」を `OnBuildRoute` スクリプトが `ModuleSearcher` で読んで組む構成 (経路マスタはただのモジュール。承認フロー側はマスタの形を知らない)
  (1: 課長承認 (必須1名) → 2: 部長または経理 = `Any` なのでどちらか1名の承認で通過)
- ログインユーザー: 申請 太郎 (申請者) / 承認 花子 (一次承認) / 決裁 次郎 (二次承認) /
  監査 四郎 (二次承認・`Any` の相方) / アドレス未登録 五郎 (アドレス空 = 異常系用)。
  各自の通知先アドレスは DB の `app_users` を見ること (役割ごとにタグを分けたプラスアドレス)

| 観点 | 確認すること |
|---|---|
| 通知の発火点 | **順番が回ってきたメンバーに送る**。申請時は一次承認者、承認して次へ進むと次の承認者。最後の承認では飛ばない |
| `Any` ステップ | 現在担当者が2人になるので**2人に通知**。どちらか1人の承認でステップ完了 |
| 却下・差し戻し → 再申請 | `AttemptNo` が +1、再申請で一次承認者に再通知。履歴 (`ApprovalHistory`) は不変で残る |
| 通知失敗は承認を止めない | アドレス未登録ユーザーを承認者にすると通知だけ失敗し、フローは進む (履歴に失敗が残る) |
| 権限 | 申請中は申請項目が編集不可、査定額は**最終承認者だけ**編集可 (PermissionField)。承認データは画面から書けない |
| 状態の正規化 | `approval_flow_members.status` は「今待っている人だけ `Waiting`」(未到達は `Pending`) |

## 6. 既知の問題・注意点 (触る前に読む)

1. **メールテスト環境の詳細画面には保存ボタンが無い** (宛先名簿だけ追加済み)。
   詳細ページは保存ボタンを自動で出さないので、受注・メール配信・ユーザーの詳細で編集内容を保存したい場合は
   各モジュールに `SubmitButtonFieldDesign` を置く必要がある (`ApprovalTest` 側の申請書には最初から有る)
2. **`MaxBulkCount` 超過は今も例外**なので、クライアントには理由が出ず `Mail request failed.` になる。
   呼び名の設定漏れ系は失敗結果に寄せた (下記) が、これは残っている
3. **メールアドレスの間違いは検知できない**。送信直前の `MimeKit` のパースで弾けるのは「壊れた文字列」だけで、
   `foo` (＠なし) / `foo@example` / ドメインのタイポは通ってしまう。存在しないアドレスは Gmail が受理して
   後から bounce が届くだけなので、履歴上は**成功**になる。必要なら宛先組み立て時の形式チェック追加を検討
4. **`appsettings.MailTest.json` / `appsettings.Approval.json` はローカル専用** (絶対パス +
   秘密を含む)。どちらも `.gitignore` で除外済み (2026-08-26)
5. `ApprovalTest` の DB は上記の検証でフローが1件進んだ状態 (購買申請「ノートPC 5台」が承認中)。
   きれいに始めたい場合は `ApprovalTest\README.md` の DB 作り直しコマンドを使う
