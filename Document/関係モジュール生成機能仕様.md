# 関係モジュール生成機能仕様

2026-08-13 検討版。承認フロー（[承認フロー機能仕様.md](承認フロー機能仕様.md) §8）の
「必要モジュールの自動生成」を汎用機能として切り出したもの。

## 目的

機能（フィールド）が動くために**決まった形の関係モジュール**が必要になるケースが増えている。
これをユーザーが手で作るのは非現実的で、機能ごとに生成コマンドを作るのも重複する。
そこで「**機能側がモジュールテンプレートを供給し、デザイナが共通の生成 UI / CLI で作る**」を
汎用の拡張ポイントにする。

生成されたモジュールは**通常のモジュール**であり、以後はユーザーの持ち物
（フィールド追加・画面カスタム・リネームすべて自由。機能側とは明示指定＋デフォルト名で結合）。
「作り込みすぎない・決めすぎない」を生成で補う——仕様を焼き込む代わりに、
**編集可能な出発点を生成する**のがこの機能の思想。

## 利用予定（順に）

| 利用者 | 生成するもの |
|---|---|
| 承認フロー（最初の利用者） | ApprovalFlow / Member / History（＋オプションで Notification / Delegation / 経路マスタ）、申請書側の結線（FK 列・dotted 宣言・DataOnlyFields・DataWriteCondition）、承認待ち一覧などのサンプル画面 |
| メール送信 | メール履歴モジュール（現状は予約名のモジュールを手で作る運用） |
| 通知 Outbox / 代理設定 | 承認フローの次増分で使う補助モジュール |
| 編集履歴フィールド（保留中） | 履歴モジュール |
| メンバー解決 | ユーザー / 部署 / グループマスタの雛形（組織バインディングの前提セット） |
| 業務テンプレの部分適用 | 「この機能に必要な画面一式だけ足す」形の部分テンプレート |

## 1. 拡張ポイント（機能側が供給するもの）

FieldCatalog にドキュメントを登録するのと同じ構図で、**モジュールセットテンプレート**を登録する。

```csharp
public class ModuleSetTemplate
{
    public string Name { get; set; }                 // 例: "ApprovalFlow"
    public string DisplayName { get; set; }          // 生成 UI に出す名前 (resx キー可)
    public string Description { get; set; }
    public List<ModuleSetVariation> Variations { get; set; }  // 例: 最小 / 標準 / フル
}

public class ModuleSetVariation
{
    public string Name { get; set; }                 // 例: "Minimal"
    public List<ModuleDesign> Modules { get; set; }  // 生成するモジュール定義 (デザインそのもの)
    public Dictionary<string, string> TableDdl { get; set; }  // DataSourceType 別の CREATE TABLE 雛形
    public Action<GenerationContext>? WireOwner { get; set; } // 配置元モジュールへの結線
                                                              // (FK列・dotted宣言・条件・フィールドのマッピング設定)
}
```

- 登録: `ModuleSetCatalog.Add(template)`（ExtrasDesignerInitializer / アプリの Designer 初期化から）
- モジュール定義は**デザインそのもの**（ModuleDesign）で供給する。テンプレート側の資産
  （保護条件・レイアウト・スクリプト）を丸ごと持てる
- DDL は雛形として提示する（実行はユーザーの確認を挟む。DB への自動適用は将来。
  デザインチェックの「テーブル不在」検出と組み合わせる）

## 2. 生成の入口と動作

- **デザイナ**: フィールド配置時に「必要なモジュールがありません。生成しますか？」の提案、
  および Tools メニューからの明示実行。バリエーション（最小/標準/フル）とプレフィックスを選ぶ
- **headless CLI**: 同じ生成をコマンドで（CCFD = Claude Code からも呼べる）
- **冪等**: 指定名のモジュールが既に存在する場合は生成せず、配置元への結線
  （フィールドのマッピング設定）だけを行う。これが「使いまわし」の実現方法
  — 2 個目以降の申請書にフィールドを置いたときは参照設定のみが走る
- **プレフィックス**: 別セットを共存させたい場合（部門ごとに承認データを分離等）は
  プレフィックス付きで生成し、マッピングもそこへ向ける
- 生成物はすべて通常のデザインファイルとして書き出す（Undo・差分・コミットの対象）

## 3. 生成後の関係

- 機能とモジュールの結合は**明示指定＋デフォルト名**（フィールドのマッピングプロパティ）。
  生成はマッピングを埋めるだけで、以後の正はマッピング
- 生成されたモジュールの改変はユーザーの自由。壊れうる約束（必須フィールド・保護条件）は
  **デザインチェックが検証**する（生成機能ではなく各機能のフィールドが持つ既存のチェック）
- 再生成は行わない（生成は出発点の提供であり、同期ではない）。
  機能のバージョンアップで必須フィールドが増えた場合はデザインチェックが指摘し、
  ユーザーが追加する（または将来の「差分生成」で補助）

## 4. 実装の置き場所

- カタログと生成ロジック: デザイナ拡張（core の Designer に `ModuleSetCatalog` 相当の
  拡張ポイントを追加するか、Designer.Standard / Extras.Designer 側で完結できるかは実装時に調査。
  デザインファイルの書き出しは既存のデザイナ保存機構を使う）
- テンプレート供給: 各機能のパッケージ（承認フローなら Extras）
- CLI: designer の headless サブコマンド群（designcheck / claude-workspace と同列）に追加

## 5. 確認項目（主要テスト観点）

- [ ] 生成（最小/標準/フル）でモジュール・結線・マッピングが揃い、デザインチェックが緑
- [ ] 冪等: 既存セットがある状態での再実行は結線のみ
- [ ] プレフィックス付き生成で別セットが共存する
- [ ] 生成後にモジュールをリネームしてもマッピングが追従する（既存のリネームリファクタ）
- [ ] CLI から同じ生成ができる
