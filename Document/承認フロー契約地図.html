承認フローの契約地図

「モジュール」と「契約（Contract）」がどうつながっているかを、この1ページだけで分かるようにまとめた。

一言でいうと
契約フィールドは、モジュールが胸につける名札。
「私はフローです。状態は Status という列に入っています」と名乗る。
なぜ必要か
エンジンは 役割名（Status / Applicant …）でしかモジュールを触らない。
実際のフィールド名は自由。翻訳表が契約。

1. 登場人物は 3 種類だけ

A
ユーザーが作る 申請書

経費申請・購買申請など。中に ApprovalFlowField を1つ置く。ここだけが業務データ。

B
エンジンだけが書く 承認データ 3 つ

フロー / メンバー / 履歴。誰も画面から書けない（UserWrite=誰も不可）。各モジュールに契約フィールドが1つ。

C
ユーザーが作る・任意 経路マスタ

経路 / ステップ / ステップ承認者（形は自由）。契約なし。申請書のスクリプトが読んで経路を組む材料で、無くても動く。

エンジンのコードには "Status" という文字列は出てこない。全部「役割 → 契約で引く → 実名」。だからユーザーが列名を 状態 に変えても動く。

4. 契約フィールドは 3 つだけ（フロー系）— 役割ごとの意味

役割名 = 既定のフィールド名。既定名で作れば設定不要（置くだけ）。無ければデザインチェックがエラー。 「型」は Example のフィールド型（契約は名前で結ぶので、値の意味が同じなら型は変えてよい。Select ↔ Text など）。 契約の役割はシステム（エンジン・UI・申請書側の条件）が読むものだけ。書くだけの項目（経路名、履歴の遷移前後ステータスなど）は契約に持たない — 欲しければモジュールに自由にフィールドを足せばよい（エンジンは触らない）。だから役割は全て必須（デザイナの表示名に「(必須)」、空ならデザインチェックがエラー）。唯一の －（任意）は通知メールのオプトイン。「書く」はその値を誰が更新するか。エンジン以外は書かないのが前提（モジュールの UserWriteCondition は誰も書けない条件にしてある）。

4.1 ApprovalFlowContract — フローモジュール（申請 1 件 = 1 行）

役割必須型意味書く主に読む
Status○Select (enum ApprovalFlowStatus)フロー全体の状態。InProgress 承認中 / Completed 承認済み / Rejected 却下 / Returned 差し戻し / Withdrawn 取り下げエンジン（全アクション）申請書の編集ロック条件（DataWriteCondition）、ステッパー UI、承認状況一覧
TargetModuleName○Text申請書モジュール名（どの種類の申請か）。フローを複数の申請書で共有するために持つエンジン（申請時）一覧の「開く」（申請書へ遷移）、エンジンの申請書保存
TargetId○Text申請書レコードの Id（逆参照）エンジン（申請時。申請書の新規保存後に確定）同上
Applicant○Link → ユーザーモジュール申請者。申請したログインユーザーの Idエンジン（申請時）申請書の「本人だけ編集可」条件（Approval.Applicant.Value）、取り下げ・再申請の本人確認、通知メールの返信先
AttemptNo○Number申請回数。初回 1。差し戻し／取り下げ後の再申請で +1。メンバー行と履歴行はこの番号で世代が分かれる（過去の申請回の承認記録はそのまま残る）エンジン（申請 = 1、再申請 = +1）エンジン（「今回の申請回」のメンバー行だけを見る）、検索用 SQL の結合条件
CurrentStepNo○Number現在のステップ番号（最初の承認ステップから始まり、承認で進む・差し戻しで戻る）。完了後は最終ステップのままエンジンステッパー UI（現在位置）、承認状況一覧の「現在ステップ／現在担当者」
Members○List → メンバーモジュール（Flow = Id で絞る）この申請の承認者行の一覧。メンバーモジュールはこの一覧の参照先として決まる（申請書側にモジュール名の設定は無い）—（参照定義）申請書側の権限条件（Approval.Members.～ のリンク越し存在条件）、ステッパー UI
Histories○List → 履歴モジュール（Flow = Id で絞る）この申請の操作履歴の一覧。履歴モジュールはこの一覧の参照先として決まる—（参照定義）ステッパー UI の履歴表示

契約外だが Example には OptimisticLocking（楽観ロック。綴り固定のシステムフィールド）を置いている。エンジンの同時更新（2 人が同時に承認）をここで検出する。

4.2 ApprovalMemberContract — メンバーモジュール（申請回 × ステップ × 承認者 = 1 行）

申請時に経路（ApprovalRouteData）を行に展開したもの。「ステップの設定」（StepType〜ReturnScope、IsFinalStep）は同じステップの全行に同じ値が入る。 経路の設定を行にコピーしておくのは、後で経路マスタを変えても進行中の申請に影響させないため。

役割必須型意味書く主に読む
Flow○Link → フローモジュール親フローエンジン（展開時）Members 一覧の絞り込み、エンジン
AttemptNo○Numberどの申請回の行か（フローの AttemptNo と同じ値）エンジン（展開時）エンジン（今回分だけ読む）
StepNo○Numberステップ番号（1 始まり。経路の順）エンジン（展開時）エンジン（進行）、ステッパー UI
StepName○Textステップの表示名（「課長承認」等）エンジン（展開時）ステッパー UI、通知メール件名、一覧
StepType○Select (enum ApprovalStepType)Approval 承認（承認されるまで次へ進まない）/ Confirmation 回覧（見るだけ。フローの進行をブロックしない。承認ではなく「確認」を記録）エンジン（展開時）エンジン、UI（ボタンの出し分け）
CompletionPolicy○Text / Select (enum ApprovalCompletionPolicy)そのステップの完了条件。RequiredMembers 必須メンバー全員（必須がいなければ誰か 1 人）/ All 全員 / Any 誰か 1 人。ステップが完了すると、まだ承認していない同ステップの人は Skipped になるエンジン（展開時）エンジン（ステップ完了判定）
IsCommentRequiredOnReject○Boolean却下・差し戻しにコメント必須かエンジン（展開時）エンジン（入力検証）、UI
ReturnScope○Text / Select (enum ApprovalReturnScope)差し戻し先の許可範囲。ApplicantOnly 申請者へ戻すだけ / AnyPreviousStep 前の任意のステップへ戻せるエンジン（展開時）エンジン、UI（差し戻し先の選択肢）
ApproverUser○Link → ユーザーモジュールこの行の承認者（解決済みのユーザー Id。役職などの解決は申請時のスクリプト側で済ませる）エンジン（展開時）「自分の番か」の判定、申請書側の権限条件、通知メールの宛先（ApproverUser.Email.Value）、承認待ち一覧
IsRequired○Boolean必須メンバーか（CompletionPolicy = RequiredMembers のときに効く）エンジン（展開時）エンジン（ステップ完了判定）
IsFinalStep○Boolean最終ステップの行か。申請書側の「最終承認者だけ査定額を編集できる」のような条件で使うエンジン（展開時）申請書側の権限条件
Status○Select (enum ApprovalMemberStatus)行の状態。Pending 順番待ち（まだ自分の番でない）/ Waiting 承認待ち（今この人の番）/ Approved 承認した / Rejected 却下した / Confirmed 回覧を確認した / Skipped 不要になった（ステップが他の人で完了）。Pending ↔ Waiting はエンジンが毎回正規化するエンジン（アクションのたび）承認待ち一覧（Waiting の行）、現在担当者、申請書側の権限条件
ActedAt○DateTimeこの人が行動した日時（承認・却下・確認）エンジンステッパー UI
TurnNotifyMail－MailField「自分の番になった」通知メール。承認で次の人が Waiting になったときにエンジンがサーバー側で送る（コミット後）。宛先・件名・本文はメールフィールドの設定で、Flow や ApproverUser のリンク越し参照が使える。未設定なら通知しない—（送信設定）エンジン（送信）

4.3 ApprovalHistoryContract — 履歴モジュール（操作 1 回 = 1 行、追記のみ）

監査用。エンジンは追記するだけで更新・削除はしない。差し戻しや再申請で状態が巻き戻っても履歴は残る。

役割必須型意味書く主に読む
Flow○Link → フローモジュール親フローエンジンHistories 一覧の絞り込み
AttemptNo○Numberどの申請回の操作かエンジンステッパー UI（今回分と過去分の区別）
Action○Text / Select (enum ApprovalAction)操作の種類。Submit 申請 / Approve 承認 / Reject 却下 / Return 差し戻し / Withdraw 取り下げ / Resubmit 再申請 / Confirm 回覧確認エンジンステッパー UI、承認状況一覧の申請日（Submit 行の ActedAt）
ActorUser○Link → ユーザーモジュール操作した人エンジンステッパー UI
Comment○Text操作時のコメント（却下理由など。IsCommentRequiredOnReject なら必須）エンジン（ユーザー入力を記録）ステッパー UI
ActedAt○DateTime操作日時エンジンステッパー UI、申請日

5. 経路マスタ（任意）に契約は無い — 承認フロー側は「経路の作り方」を知らない

フィールドが経路について知るのは 1 点だけ: OnBuildRoute スクリプトが ApprovalRouteData（解決済みユーザー Id のステップ列）を返す。それをどう組むかは全部スクリプトの書き方の違いで、マスタ自体も必須ではない。

Example の経路マスタ（ただのモジュール 3 つ）を読むスクリプト

契約が無いので、フィールド名も形も自分で決めてよい。読む処理は経路マスタモジュール側のスクリプト（ApprovalRoute.mod.cs）に 1 つ置き、申請書からはモジュールを new して呼ぶ（static 関数は未サポート）:

// 申請書 (ExpenseRequest.mod.cs) ApprovalRouteData OnBuildRoute() { return new ApprovalRoute().Load("経費ルート"); } // 経路マスタ (ApprovalRoute.mod.cs) — 形を知っているのはここだけ ApprovalRouteData Load(string routeName) { var routes = new ModuleSearcher<ApprovalRoute>(); routes.AddEquals(r => r.RouteName.Value, routeName); var master = routes.ExecuteFirstOrDefault(); if (master == null) { Logger.Error("経路マスタに『" + routeName + "』がありません"); return null; } var steps = new ModuleSearcher<ApprovalRouteStep>(); steps.AddEquals(s => s.Route.Value, master.Id.Value); steps.OrderBy(s => s.StepNo.Value); var route = new ApprovalRouteData(); route.Name = master.RouteName.Value; foreach (var s in steps.Execute()) { var step = route.AddStep(s.StepName.Value); if (s.CompletionPolicy.Value != null && s.CompletionPolicy.Value != "") step.CompletionPolicy = s.CompletionPolicy.Value; var members = new ModuleSearcher<ApprovalRouteStepMember>(); members.AddEquals(m => m.Step.Value, s.Id.Value); foreach (var m in members.Execute()) { if (m.ApproverUser.Value == null) continue; if (m.ApproverUser.Value == CurrentUser.Id.Value) { Logger.Error("申請者自身が承認者に含まれる経路では申請できません"); return null; } step.AddMember(m.ApproverUser.Value, m.IsRequired.Value ?? true); } } return route; }

役職ベースにしたければ Load の AddMember の前に「ユーザーモジュールを役職＋申請者の部署で検索」を挟むだけで、全申請書に効く。購買申請は金額で経路名を切り替えてから Load している。セットアップ（自動生成）はこの 3 モジュール＋ ApprovalRoute.mod.cs（Load）＋申請書側の 1 行雛形を「出発点」として吐くだけで、以降は同期しない。

なぜ契約を消したか: 以前は経路契約 3 つ＋ RouteModuleName ＋ LoadRoute があったが、フィールドがマスタの「形」を知っている構造だと、形を変えると契約・API・UI が連鎖して変わり、役職ベース（行 = 「部長」であって人ではない）が「1 行 = ユーザー 1 人」の契約に乗らず、ユーザーのカスタマイズ余地を Extras が先回りして塞いでいた。エンジンは解決済みユーザーのスナップショットしか受け取らないので、経路作成時に人に固定される限りフロー側はそのままで足りる。

7. ここでよく混乱する

契約フィールドは DB 列を持つ？ 画面に出る？
どちらも持たない。設定を運ぶだけのフィールド（PermissionField と同じ流儀）。テーブルに列は要らない。
申請書側でメンバー・履歴モジュール名を指定する場所が無い
指定しないのが正しい。フロー契約の Members / Histories 一覧の参照先モジュールが自動的にそれ。複数の申請書が同じ承認モジュールを共有できるのはこのため。
役割を空にするとどうなる？
「使わない」宣言。チェック対象外になる。TurnNotifyMail が空 = 通知なし。
同じモジュールに契約を2つ置いたら？
デザインチェックがエラー。どちらの翻訳表を使うか決められないため。
経路マスタに契約が無いなら、マスタの実装漏れはどう気づく？
デザインチェックではなく、スクリプトのコンパイルエラー／実行時の null 中止で気づく。経路マスタは申請書スクリプトの都合で決まるものなので、そこは割り切っている。
申請書の編集ロックはどこ？
申請書の DataWriteCondition に Approval.Status == null OR IN(Returned, Withdrawn, Rejected) と書く（リンク越しスカラー参照）。契約とは別レイヤー。「最終承認者だけ査定額を書ける」は Approval.Members.IsFinalStep / Status / ApproverUser のリンク越し存在条件で PermissionField に書く。
Status の値は誰が決めている？
Extras の C# enum（ApprovalFlowStatus 等）を [DesignEnum] で公開したもの。メンバー名 = 保存値。SelectField の候補にはそれを使うので内部値を手書きしない。
