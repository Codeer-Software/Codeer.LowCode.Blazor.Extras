# メール送信機能仕様

2026-08-09 検討確定版（同日改訂: MailField案を廃止し、スクリプトAPI＋サーバーサービスの2口に変更。
同日再改訂: テンプレ変数をデザイン変数表記に統一しリンクパス対応、ノーコード入口として **BulkMailField** を追加、
BulkMail スクリプトオブジェクトとクライアント解決 /bulk 経路を削除=一斉送信は BulkMailField に一本化）。正典とする。

## 目的とスコープ

メール機能は**送信だけ**を提供する。いつ送るか・送ってよいかの判断はすべて利用側の責務。
利用の入口は3つ:

```
IMailSender 群（名前付き送信インフラ: SMTP / Microsoft Graph / SendGrid）
   ↑
MailDispatcher（テンプレ解決・一斉送信・履歴・誤送信防止を持つサーバーサービス）
   ↑                      ↑                        ↑
スクリプト(Mail=単発)       カスタムフィールド・将来の    BulkMailField(一斉送信ボタン=一斉送信の唯一の入口。
                          スケジューラ等(サーバー直)     §8。内部はbulk_search経路)
```

- **ノーコードの定型は BulkMailField**（§8）: キャンペーンレコード＋名簿/条件リストの構成をデザイナだけで組める
- **単発送信はスクリプト**: `Mail` オブジェクト。送信ボタンは ButtonField ＋ OnClick、保存時通知は保存後イベント、で既存機構に乗せる
- **機能（承認フローフィールド等のカスタムフィールド・将来のスケジューラ）が使うのはサーバーサービス**: `MailDispatcher` を直接呼ぶ。宛先・文面は呼び出し側が作って渡す

**非スコープ（別機能・将来）**
- スケジューラ（時間起点: リマインダー・定期サマリー）— 別機能。MailService はサーバー単体で呼べるのでそのまま乗る
- 公開エンドポイント（配信停止リンク・開封/バウンス Webhook・メール内ワンクリック承認）— 利用側機能が「トークン付き公開エンドポイント」共通基盤（将来）の上に公開する
- メール受信（POP/IMAP取り込み）
- 送信の非同期ジョブ化・進捗表示 — v1 は同期＋件数上限。大量送信の可否は選んだインフラの性質（下記）
- テンプレ文面の静的検証（デザインチェック・リネーム追従）— テンプレはスクリプト文字列またはデータ（テンプレモジュール）の世界なので対象外。文面をユーザーが編集する SFA 用途ではテンプレモジュール（通常のモジュール設計）を推奨
- 宛先ごとに異なる添付（帳票の一括送付）— v1 の一斉送信の添付は全宛先共通のみ。個別添付はスクリプトで1通ずつ `Send`

## 1. 送信インフラ（名前付き MailSenders）

### 設定 (appsettings.json)

DataSources / FileStorages と同型の名前付き設定。キー・シークレットはサーバー側でのみ解決し、クライアントにはセンダー名しか渡らない。

```json
"Mail": {
  "AppBaseUrl": "https://app.example.co.jp",
  "RedirectAllTo": "",
  "Senders": [
    { "Name": "Notify",   "Type": "GraphApi", "TenantId": "...", "ClientId": "...", "ClientSecret": "...",
      "SenderMailAddress": "system@example.co.jp", "SenderDisplayName": "業務システム" },
    { "Name": "Campaign", "Type": "SendGrid", "ApiKey": "...",
      "SenderMailAddress": "info@example.co.jp", "MaxBulkCount": 10000 },
    { "Name": "Local",    "Type": "Smtp", "Host": "smtp.example.local", "Port": "587", "SSL": "true",
      "SenderMailAddress": "noreply@example.local", "Password": "..." }
  ]
}
```

- 値は環境変数で上書き可能（標準の構成バインド。AI設定の `AZURE_OPENAI_*` と同じ流儀）
- `Senders[0]` が既定センダー（センダー名省略時に使用）
- **後方互換**: 既存の `MailSettings`（単一SMTP設定）が存在する場合、`Type=Smtp` / `Name=Default` のセンダーとして読み込む。既存の `Mail.Send(message)` スクリプトはそのまま動く
- `MaxBulkCount`: 一斉送信の件数上限（既定 10000）。超過はエラー（黙って切り詰めない）
- `AppBaseUrl`: `{RecordUrl}` 差し込み（後述）に使用。承認通知等のディープリンク用

### プロバイダ（v1 は 3 種）

| Type | 実装 | 用途の目安 |
|---|---|---|
| `Smtp` | MailKit (MIT) に刷新。`System.Net.Mail.SmtpClient`（MS非推奨）は廃止 | オンプレ・社内メールサーバー |
| `GraphApi` | HttpClient 直（client credentials でトークン取得 → sendMail）。SDK は使わない | M365 圏の通知系（自社ドメインから送る）。Exchange Online のレート制限（毎分30通級）があるため一斉送信には不向き |
| `SendGrid` | HttpClient 直（/v3/mail/send）。SDK は使わない | 一斉送信・到達性が必要な外部向け配信。personalizations でネイティブバルク（1リクエスト1000宛先） |

- **SDK をパッケージに焼き込まない**（DBプロバイダと同じ方針）。3種とも素の REST なので HttpClient で依存ゼロ実装。SigV4 署名が必要な Amazon SES は v1 対象外
- 大量送信の可否はインフラの性質。「一斉送信は SendGrid 系センダーを使う」ことをドキュメントで案内する

### IMailSender（公開・差し替え可能）

DbAccessor と同じ流儀で public にし、独自プロバイダ（社内メールGW等）を差し込めるようにする。

```csharp
public interface IMailSender
{
    Task<MailSendResult> SendAsync(MailMessage message);
    //テンプレ＋宛先ごとの差し込み変数。ネイティブバルクのあるプロバイダはそれにマップ、
    //無いプロバイダは共有テンプレエンジンで解決して逐次＋レート制御
    Task<MailSendResult> SendBulkAsync(MailTemplate template, List<MailBulkRecipient> recipients);
}

public class MailSendResult
{
    public int TotalCount { get; set; }
    public int SuccessCount { get; set; }
    public List<MailSendFailure> Failures { get; set; } = new(); // { To, Error }
    public bool IsSuccess => Failures.Count == 0;
}
```

- **部分失敗の報告は契約**。全成功/全失敗の bool では一斉送信に使えない
- `MailBulkRecipient` = { To, Cc, Bcc, Variables(差し込み変数名→値) }
- 一斉送信のリクエストは「共通部分（件名・本文の雛形・添付）＋宛先ごとの変数リスト」で運ぶ（解決済み全文1万通を運ぶと数十MBになるため。SendGrid の personalizations にそのままマップできる）。`MailBulkTemplate`（共通部分の箱）は IMailSender 契約専用で、ワイヤには乗らない（リクエストDTOはフラット。サーバーが詰め替える）

### 誤送信防止（RedirectAllTo）

- `Mail.RedirectAllTo` が設定されていると、**全プロバイダ共通層で** To/Cc/Bcc をこのアドレスに差し替えて送る（開発・検証環境用）
- 元の宛先はメールヘッダ `X-CLB-Original-To` に記録（本文は改変しない）。3プロバイダともカスタムヘッダ対応
- 一斉送信時は宛先数分送らず、先頭 10 通のみ転送＋総件数をヘッダに記録（検証環境で1万通飛ばさない）

## 2. テンプレート解決エンジン（共有）

- 共有コード（クライアント/サーバー同一アセンブリ）に 1 実装。スクリプトのプレビュー・個別文面組み立てと、サーバーのバルク解決で同じ結果になる
- 構文（2026-08-09再改訂: **デザイン変数と同じ表記に統一**。Excel テンプレの `$Email.Value` や Variable の `"Id.Value"` と同じ言語感覚）:
  - トークンは `VariableName`（フィールドパス＋メンバー）として解釈。末尾セグメントが既知メンバー（`Value` / `DisplayText`）のときだけメンバー扱い
  - `{Name}`（メンバー省略）: **表示文字列**（Select/Link は表示名、数値・日付はフィールドの外部テキスト書式）
  - `{Name.Value}`: 値。Select/Link は**コード値**。数値・日付は外部テキスト書式で整形（メールはセル書式のないテキスト媒体のため。Excel との意味差は媒体差として割り切る）
  - `{Rank.DisplayText}`: 表示テキスト（Select/Link のみ。他は空文字）
  - `{Contact.Email.Value}`: **リンクパス**（Link/SelectField の参照先モジュールのフィールド）。リスト取得データが `"Contact.Email"` キーで持つ値をそのまま使う。サーバー解決経路では SelectFields にフィールドパスを積むだけでデータ層（JOIN/バッチIN）が解決する＝安価
  - `{{` `}}` は `{` `}` のリテラル
- `EmailAddressVariable` / `OptOutVariable` も同じ表記（`"Email.Value"`、リンクパス可、末尾メンバー省略可）
- 組み込み変数: `{RecordUrl}`（`Mail.AppBaseUrl` ＋ モジュールURLセグメント ＋ Id で生成。AppBaseUrl 未設定で使うと実行時エラー）
- `IsBodyHtml=true` のとき差し込み値は HTML エスケープする（インジェクション防止）。テンプレ自体はエスケープしない（設計者が書くHTML）
- 差し込みコンテキスト: 単発送信＝渡した Module/ModuleData、一斉送信＝宛先行
- 存在しないフィールド名は空文字に解決（実行時に落とさない。テンプレはデータ由来のため静的検証はしない）
- リンクパスの書式整形（リンク先の日付書式等）はデザイン検索デリゲート（サーバー=DesignData、クライアント=AppInfoService）がある場合のみ。無い環境では ToString になるだけで解決自体は成立する

## 3. スクリプト API（Mail オブジェクト）

（2026-08-09改訂: サービス中心の `MailService.Send(...)` を廃止し、オブジェクト中心に破壊的変更。
全設定はプロパティ、`Send()` は引数なし、戻り値は `MailSendResult` に統一。
同日再改訂: **BulkMail スクリプトオブジェクトは削除**。一斉送信の入口は BulkMailField（§8）に一本化し、
クライアント解決の `/bulk` 経路もワイヤごと廃止＝宛先アドレスがクライアントに一切下りないことが構造で保証される）

```csharp
//単発
var mail = new Mail();
mail.Sender = "Notify";           //Mail.Senders の名前(省略時は先頭)
mail.AddTo("a@example.com");      //To/Cc/Bccは複数あるのでAddメソッド(";"区切り可)
mail.Subject = "承認依頼";
mail.Body = "本文";                //HTMLは IsBodyHtml = true
mail.AddAttachment("見積.xlsx", excel);
mail.Source = this;               //履歴のSourceModule/SourceId(省略可)
var result = mail.Send();         //MailSendResult (IsSuccess/Failures)
```

- 一斉送信は BulkMailField（§8）。スクリプトからは `BulkMail1.Send()`（フィールドのスクリプトAPI）で起動できる
- 少数の宛先へのスクリプト送信（通知等）は `Mail` をループで（履歴は1通1レコード）
- BulkMail 削除で失うもの（承知の上の割り切り）: 一斉送信への添付（将来は BulkMailField に FileField 参照で回収）/
  キャンペーンレコードなしのアドホック一斉送信（履歴の起点も文面の記録も残らない運用なので v1 で塞ぐのはむしろ健全）/
  Preview（将来はフィールドの確認ダイアログに組み込み）
- 配線は `MailTransport`（static。エンドポイントURL2つ＋差し替え口 `IMailTransportHandler` 1つ）に集約。ハンドラは**HTTP POSTの置き換え**で、エンドポイントにPOSTするものと同じリクエストDTO（`MailSendRequest` / `MailBulkSearchRequest`）をそのまま受ける。リクエストDTOは**フラット**（Template入れ子なし。EmailAddressVariable/OptOutVariableはbulk_searchリクエストの持ち物）で、コントローラは `MailDispatcher.SendAsync(request)` / `MailBulkSearch.SendAsync(..., request)` に渡すだけの薄い形。デスクトップはこれを1クラス実装してセットする（HTTPを通さず MailDispatcher へ直結）。単発送信もクエリパラメータではなく `MailSendRequest`（SenderName＋Message＋Source）をPOSTする。旧 `MailService`/`MailMessage`/`MailTemplate` のスクリプト公開は廃止（ワイヤ型として存続。MailMessageは純DTO）
- サーバーコードから宛先リストを組んで送る口は `MailDispatcher.SendBulkAsync(senderName, template, recipients, source)`（公開）が引き続き存在する（承認フローフィールド等の将来のサーバー側利用者向け）

## 4. サーバーサービス（MailDispatcher）

承認フローフィールド等のカスタムフィールド実装・アプリコード・将来のスケジューラが、UI文脈なしで直接呼ぶ公開サービス。スクリプトAPIも内部ではこれに乗る。
（クラス名はスクリプトオブジェクトの `MailService` と衝突するため `MailDispatcher`）

```csharp
public class MailDispatcher   // Extras.Server。公開
{
    public MailDispatcher(MailConfig config, Func<MailSenderSettings, IMailSender?>? customSenderFactory = null);
    Task<MailSendResult> SendAsync(string? senderName, MailMessage message);   // Phase2で source(履歴紐づけ) を追加
    Task<MailSendResult> SendBulkAsync(string? senderName, MailBulkTemplate template, List<MailBulkRecipient> recipients);
    //Phase2: searcher相当のサーバー解決版（SearchConditionと宛先/除外フィールド名から recipients を組み立てて送る）
}
```

- センダー解決（名前→IMailSender）、テンプレエンジン、RedirectAllTo、MaxBulkCount、履歴書き込みはすべてこの層。プロバイダは送るだけ
- 呼び出し側（承認フロー等）は宛先と文面を**作って渡す**。判断（誰に・いつ・送ってよいか）は呼び出し側の責務

## 5. 送信履歴

**送信1回＝履歴モジュールに1レコード INSERT**。その回の失敗明細だけを JSON でひとつの列にまとめる（1万件送信の次の1万件は別レコード）。

- 履歴の有効化は**サーバー設定 `Mail.HistoryModuleName` を1つ**（Extras完結のためデザインデータ側ではなくappsettings。コアのAppSettings変更を避ける）。設定があれば**全送信**（単発・一斉とも）をサーバー側で自動記録、無ければ記録しない。送信のたびにスクリプトで指定はしない
- 履歴モジュールのフィールドは**予約名の綴り一致**で自動マップ（置いたフィールドだけ書かれる）:
  `SentAt`(DateTime) / `SenderName`(Text) / `Subject`(Text) / `TotalCount`(Number) / `SuccessCount`(Number) /
  `FailureDetails`(Text または JsonField。`[{"To":"...","Error":"..."}]`) / `SourceModule`(Text) / `SourceId`(Text)
- CreatedAt / Creator はシステムフィールドとして通常どおり自動
- **書き込みはサーバー内部経路**。送信操作したユーザーの履歴モジュールへの書き込み権限に依存しない（履歴はシステムの記録）
- 失敗明細の切り詰めはしない（1送信1レコードのため肥大は行単位で分散する）
- 明細の画面表示は `FailureDetails` 列を ListField データオーナーモード（DbColumn）で一覧化できる
- 検証は実行時（デザインチェックのアプリレベル拡張点がExtrasに無いため）: `HistoryModuleName` のモジュールが存在しない・予約名フィールドの型が不正な場合は送信時にエラーログ。送信自体は失敗させない（履歴は送信の従属機能）
- 内部書き込みの実装: コアに権限バイパスの公開書き込みAPIは無いため、アプリテンプレートの CustomizedModuleDataIO（protected AddAsync を持つ同梱ソース）に内部書き込み用の口を設け、MailService へ注入する

## 6. 実装配置

- 既存のメール実装（`MailMessage` スクリプトオブジェクト / `SmtpMailService` / MailController）が Extras にあるため、**本機能も Extras に実装**する
  - `Codeer.LowCode.Blazor.Extras`（共有）: テンプレ解決エンジン / MailTemplate / MailResult / Mail スクリプトオブジェクト拡張
  - `Codeer.LowCode.Blazor.Extras.Server`: IMailSender / 3プロバイダ / MailService（共通層・履歴書き込み）
  - アプリテンプレート: MailController を「センダー名指定＋バルク＋searcher解決＋source」対応に拡張（同梱ソース＝ユーザーがカスタマイズ可能な層）
- **コア（Codeer.LowCode.Blazor）は変更しない**（Extras＋テンプレートで完結することを確認済み）。テンプレエンジンの表示文字列変換（SelectField表示名・日付フォーマット等）はコアの公開型（FieldDataBase/FieldDesignBase派生）からExtras側で実装する
- 依存追加は MailKit のみ（MIT）

## 7. フェーズ分割

**Phase 1: インフラ層 — 実装済み (2026-08-09, Extras 0.6.0)**
名前付き Mail.Senders ＋ IMailSender ＋ Smtp(MailKit 4.17.0)/GraphApi/SendGrid ＋ RedirectAllTo ＋ 部分失敗結果 ＋ 既存 `Mail.Send(message)` の載せ替え（互換維持）
- （改訂: 当初センダー名はクエリ`?sender=`で運んだが、スクリプトAPI刷新時に `MailSendRequest` のPOSTに統一。旧コントローラとのワイヤ互換は破棄=テンプレ更新とセット）
- デスクトップ(WinForms/Wpf)は新フック `MailService.SendMailWithSenderAsyncCore` で MailDispatcher に直結（旧 `SendMailAsyncCore` も残置）
- 旧 `SmtpMailService` は互換シムとして残し、内部は MailKit（`System.Net.Mail.SmtpClient` は撤去）

**Phase 2: 一斉送信・履歴 — 実装済み (2026-08-09, Extras 0.6.0)**
テンプレ解決エンジン（共有・GetVariableNames追加）＋ MailVariableResolver（表示文字列化。Select/LinkはDisplayText、数値/日付はIExternalTextFormatFieldDesign）＋ `MailService.SendBulk`（recipients / rows / searcher ×source有無の6オーバーロード）＋ `CreateTemplate`/`CreateRecipient`/`Fill` ＋ `Mail.HistoryModuleName`（サーバー設定・自動記録）＋ ScriptObjectDocs
- スクリプトオブジェクト名は既存どおり **MailService**（`MailService.SendBulk(...)`）
- サーバー: `/api/mail/bulk`（解決済み宛先）・`/api/mail/bulk_search`（サーバー宛先解決 = MailBulkSearch。ModuleDataIO.GetListAsync経由なので読み取り権限・行条件が効く）
- `{RecordUrl}` は **searcher経路（サーバー解決）のみ**対応（`AppBaseUrl/{メインPageFrame}/{モジュール名}/{Id}`）。rows/Fill経路では解決されない
- 履歴書き込みはテンプレの CustomizedModuleDataIO.AddSystemRecordAsync（protected AddAsync 経由の内部経路）
- デスクトップ(WinForms/Wpf)は Services/MailHooks.cs で3フック（単発/bulk/bulk_search）を直結（Task.RunでUIスレッド回避）
- 一斉送信の宛先0件は送信なしの成功（0/0）。宛先なし・除外フラグtrueの行はスキップ

**Phase 3: 変数表記統一＋BulkMailField — 実装済み (2026-08-09, Extras 0.6.0)**
- テンプレ変数を VariableName 表記に統一（§2）。`{Name}` 形式も表示文字列として引き続き動く（後方互換）
- リンクパス対応: MailVariableResolver が `"Contact.Email"` キー＋メンバーで解決、MailBulkSearch の SelectFields
  フィルタを「ルートフィールド存在」判定に修正（従来はリンクパスが黙って落ちていた）
- BulkMailField 追加（§8）。宛先変数の候補ピッカー（`RelativeField`=他フィールドが指すモジュールの候補表示）は
  **コアデザイナ側の将来改修**（本作業は Extras 以外を触らない方針のため未実装。Extras 側に
  ModuleMember+RelativeField 属性は付与済みで、現行デザイナでは候補なし=テキスト入力に安全に退化。
  対応デザイナが出れば候補表示が有効になる）
- プロパティ名は Salesforce 用語に統一: RecipientListFieldName / EmailAddressVariable / OptOutVariable
- **BulkMail スクリプトオブジェクト削除**（同日）: 一斉送信は BulkMailField に一本化。クライアント解決の
  `/bulk` 経路（MailBulkRequest / MailTransport.SendBulkAsync / IMailTransportHandler.SendBulkAsync /
  MailRecipient スクリプトオブジェクト）もワイヤごと廃止。`MailDispatcher.SendBulkAsync(senderName, template,
  recipients, source)`（サーバー側公開API）と bulk_search 一式は存続

**将来（別機能）**: スケジューラ / トークン付き公開エンドポイント（配信停止・ワンクリック承認・Webhook）/ 宛先別添付の一括帳票送付 / SES・ACS プロバイダ / 承認フローフィールド（MailDispatcher のサーバー側利用者）/ BulkMailField の対象取込ボタン組み込み（名簿への差分取込）・メンバー行への送達結果書き戻し

## 8. BulkMailField（ノーコードの一斉送信ボタン）

SFA のキャンペーン配信を想定した定型: **配信メール自体が1レコード**（件名・本文テンプレはただのフィールド＝データ）で、
宛先は同一モジュール上のリストフィールドを参照する。
**仕様は Salesforce（Campaign + CampaignMember + List Email）に寄せる**（後追いの利点=先行者の型をそのまま取る。オリジナリティ不要）:

- **宛先リストの行 = 送る対象そのもの**。「今回はこの人を外す」は行の削除（メンバーシップの操作）。
  除外フラグで名簿を汚さない（Salesforce でキャンペーン対象を外す＝メンバーを消す、と同じ）
- **配信停止（オプトアウト）は人の恒久属性**（Salesforce の Email Opt Out = `HasOptedOutOfEmail` 相当）。
  `OptOutVariable` がリンクパスで人側の Boolean を指し、送信時に常にスキップ（キャンペーンに関係ない最終安全弁）
- 運用フロー: キャンペーン作成 → 対象取込（条件検索→名簿へ一括生成。Salesforce の Add to Campaign 相当。
  v1 はスクリプトボタン/CSV取込/手動行追加）→ 精査（行の追加・削除）→ 保存 → 送信

```
メール配信 (MailCampaign)          … 1レコード = 1配信
├── Title (Text) / Body (Text複数行)   … テンプレート(データなので配信ごとに可変)
├── Members (DetailListField → 配信対象)  … 送る対象そのもの。または条件バインドの ListField
└── BulkMail1 (BulkMailField)
      RecipientListFieldName: Members / EmailAddressVariable: Contact.Email.Value
      OptOutVariable: Contact.メール拒否.Value (人側の配信停止=最終安全弁)
      SubjectVariable: Title.Value / BodyVariable: Body.Value / DbColumn: send_summary

配信対象 (CampaignMember)              … Salesforce の CampaignMember と同型
└── Campaign (Link) / Contact (Link → 担当者)   … 精査=行を足す/消す

担当者 (Contact)
└── Email (Text) / メール拒否 (Boolean)  … 配信停止は人に付く
```

- **送信は常に bulk_search（サーバー解決）経路**。リストの `GetSearchCondition()`（親バインド解決済み）から
  `LimitCount=null` で全件対象（画面のページング・列に縛られない）。宛先アドレスはクライアントに渡らない
- **未保存ガード**: `Module.IsNewData || IsModified` の間は送信不可（保存済み=サーバーから見える状態が送信対象。
  画面の未保存編集が「効いていないのに送れる」事故を防ぐ）
- 送信前に対象件数の確認ダイアログ。配信停止行・アドレス空行はサーバーでスキップ
- **送信結果サマリ**: `DbColumn` 設定時、`BulkMailSummaryEntry` の JSON 配列（新しい順・最大20件、失敗明細は先頭5件＋全数）を
  レコードの列へ**サーバー内部経路**（履歴と同じ `CustomizedModuleDataIO.UpdateSystemRecordAsync`＝protected UpdateAsync）で書き戻す。
  サマリ失敗は送信を失敗させない（ログのみ）。全量監査は従来どおり `Mail.HistoryModuleName`（任意）と二層
- `Source`（履歴の SourceModule/SourceId）はボタンが置かれたレコードで自動
- スクリプト API: `BulkMail1.Send()`（確認ダイアログ・トーストなしで送信し `MailSendResult` を返す）
- デザインチェック: リスト参照の存在/型、宛先変数（リンクパスは Link/Select の参照先を辿って最終フィールドまで検証）、
  テンプレ変数（自モジュール）、件名/本文の未設定。リネーム追従はリスト名・自モジュール変数・宛先モジュールの単純変数
  （リンクパスは既存のリンク越し変数と同じく非追従）
- デザイナ候補: EmailAddressVariable/OptOutVariable には `ModuleMember(SearchCondition.ModuleName)`＋`RelativeField(RecipientListFieldName)` を
  付与済み。ただし候補表示にはコアデザイナ側の RelativeField 対応（将来改修・未実装）が必要で、
  **現行デザイナでは候補なし=テキスト入力**（属性は null 安全に無視される）
- Salesforce から次に取るもの（将来）: **メンバー状態**（CampaignMemberStatus 相当。送信済み/失敗を名簿行へ書き戻し→失敗のみ再送）、
  対象取込の組み込み（Add to Campaign 相当・差分取込）、配信停止リンク・開封/バウンス Webhook（公開エンドポイント基盤待ち）
