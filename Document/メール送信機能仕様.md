# メール送信機能仕様

2026-08-09 検討確定版（同日改訂: MailField案を廃止し、スクリプトAPI＋サーバーサービスの2口に変更。
同日再改訂: テンプレ変数をデザイン変数表記に統一しリンクパス対応、ノーコード入口として **BulkMailField** を追加、
BulkMail スクリプトオブジェクトとクライアント解決 /bulk 経路を削除=一斉送信は BulkMailField に一本化）。正典とする。

## 目的とスコープ

メール機能は**送信だけ**を提供する。いつ送るか・送ってよいかの判断はすべて利用側の責務。
利用の入口は3つ:

```
IMailSender 群（名前付き送信インフラ: SMTP / Microsoft Graph / SendGrid）
   ↑
MailDispatcher（テンプレ解決・一斉送信・履歴・誤送信防止を持つサーバーサービス）
   ↑                      ↑                        ↑
MailField(単発送信の唯一の入口。 カスタムフィールド・将来の  BulkMailField(一斉送信ボタン=一斉送信の唯一の入口。
                          スケジューラ等(サーバー直)     §8。内部はbulk_search経路)
```

- **ノーコードの定型は BulkMailField**（§8）: キャンペーンレコード＋名簿/条件リストの構成をデザイナだけで組める
- **単発送信は MailField**: 値と変数のペア (値優先)。値はスクリプトから設定できるため動的送信も同じ入口。**レイアウトに置くと送信ボタンとして表示** (押したら送信)。前処理を挟むなら ButtonField ＋ OnClick、保存時通知は保存後イベント、で既存機構に乗せる
- **機能（承認フローフィールド等のカスタムフィールド・将来のスケジューラ）が使うのはサーバーサービス**: `MailDispatcher` を直接呼ぶ。宛先・文面は呼び出し側が作って渡す

**非スコープ（別機能・将来）**
- スケジューラ（時間起点: リマインダー・定期サマリー）— 別機能。MailService はサーバー単体で呼べるのでそのまま乗る
- 公開エンドポイント（配信停止リンク・開封/バウンス Webhook・メール内ワンクリック承認）— 利用側機能が「トークン付き公開エンドポイント」共通基盤（将来）の上に公開する
- メール受信（POP/IMAP取り込み）
- 送信の非同期ジョブ化・進捗表示 — v1 は同期＋件数上限。大量送信の可否は選んだインフラの性質（下記）
- テンプレ文面の静的検証（デザインチェック・リネーム追従）— テンプレはスクリプト文字列またはデータ（テンプレモジュール）の世界なので対象外。文面をユーザーが編集する SFA 用途ではテンプレモジュール（通常のモジュール設計）を推奨
- 宛先ごとに異なる添付（帳票の一括送付）— v1 の一斉送信の添付は全宛先共通のみ。個別添付はスクリプトで1通ずつ `Send`

## 1. 送信インフラ（"Mail" は共通・プロバイダは独立セクション）

### 設定 (appsettings.json)

**`Mail` は製品（共通層）が読む設定だけ**。プロバイダごとの設定は形が違いすぎるので共通の器に入れず、
**独立したセクションとして定義し、使う側（テンプレートの対応表）が個別に読み出す**（差は `IMailSender` が吸収）。
キー・シークレットはサーバー側でのみ解決し、クライアントには「送信先の呼び名」しか渡らない。

```json
"Mail": {
  "DebugRedirectAllTo": "",
  "HistoryModuleName": "MailHistory",
  "UserModuleName": "AppUser", "UserEmailFieldName": "Email", "UserNameFieldName": "Name",
  "DefaultInfraName": "GraphApi",
  "DefaultBulkInfraName": "SendGrid"
},

"Smtp":     { "SenderMailAddress": "noreply@example.local", "Host": "smtp.example.local", "Port": "587", "SSL": "true", "Password": "..." },
"GraphApi": { "SenderMailAddress": "system@example.co.jp", "SenderDisplayName": "業務システム", "TenantId": "...", "ClientId": "...", "ClientSecret": "..." },
"SendGrid": { "SenderMailAddress": "info@example.co.jp", "ApiKey": "...", "MaxBulkCount": 10000 },
"Gmail":    { "SenderMailAddress": "notify@example.co.jp", "ClientSecret": "...", "TokenSecret": "...",
              "UserTokenFieldName": "GmailToken", "TokenEncryptionKey": "..." }
```

- プロバイダ設定のセクション名は**アプリが決める**（テンプレの `Program.cs` が `GetSection("Gmail")` のように個別に読む）。
  製品の型は `SmtpSettings` / `GraphApiSettings` / `SendGridSettings` / `GmailSettings`
- 値は環境変数で上書き可能（標準の構成バインド。AI設定の `AZURE_OPENAI_*` と同じ流儀。例 `Gmail__TokenEncryptionKey`）
- **差出人はプロバイダごとに1つ**（`SenderMailAddress`）。あとは「自分を差出人にする」フラグで本人か既定かの2値
  （§差出人）。だから「同一プロバイダで複数の差出人アドレス」という概念は無い
- **呼び名の解決**: 単発 = 明示名 → `DefaultInfraName`、一斉 = 明示名 → `DefaultBulkInfraName` → `DefaultInfraName`。
  どちらも空なら空のまま対応表に渡り、対応表の既定が答える（§独自インフラの差し込み）。
  対応表が知らない呼び名は**エラー**（黙って別のインフラで送らない。「先頭に落とす」規則は廃止）。
  「単発は通知系(Graph/SMTP)、一斉は配信サービス(SendGrid)」の対はこの2つの既定で固定し、
  スクリプト/フィールド側では呼び名を書かないのが基本形
- **後方互換**: 既存の `MailSettings`（単一SMTP設定）は `SmtpSettings.Normalize` で `Smtp` セクションに写す（`Smtp` に設定があればそちらを優先）
- `MaxBulkCount`: 一斉送信の件数上限（プロバイダ設定・既定 10000）。超過はエラー（黙って切り詰めない）。
  上限は `IMailSender.MaxBulkCount` として共通層に見えている
- `Mail.UserModuleName` / `UserEmailFieldName` / `UserNameFieldName`: 操作ユーザーの情報を解決するユーザーモジュールの指定。
  「自分を差出人にする」（下記）と GmailApi のユーザー単位トークン検索が使う

### 差出人（IsFromCurrentUser =「自分を差出人にする」フラグ）

**差出人はアドレス指定できない**。選べるのは2値だけで、なりすましを構造的に排除する
（2026-08-24 改訂: 旧 FromVariable/From + AllowedFromDomains のアドレス指定方式を廃止。
ドメイン枠では同ドメイン内の他人への社内なりすましが素通りだった。Salesforce も差出人は
「本人 or 検証済み組織アドレス」であり、アドレス自由指定はさせない）。

- **false（既定）**: 送信インフラ設定の差出人（`SenderMailAddress` = システムのアドレス）。
  部署共通アドレス等はインフラを分けて表現する（Notify=system@ / Campaign=info@ など）
- **true**: **操作ユーザー本人**。サーバーが認証ユーザー Id → `Mail.UserModuleName` の
  `UserEmailFieldName` / `UserNameFieldName` でアドレスと表示名を解決する。
  ワイヤ（MailSendRequest / MailBulkSearchRequest）にはフラグだけが乗り、
  クライアントが載せた From は**常に破棄**される（細工リクエストでも偽装不可）。
  未設定・アドレス未登録は送信失敗（履歴にも記録）
- 入口: MailField / BulkMailField の `IsFromCurrentUser`（MailField はスクリプトからも設定可）
- インフラごとの挙動（本人 From の実現方法）: SMTP = From ヘッダ差し替え（サーバーの SendAs 許可が前提）/
  SendGrid = from 差し替え（ドメイン認証済みなら可）/
  **GraphApi = そのユーザーのメールボックスから送信**（`/users/{from}/sendMail`。送信済みアイテムも本人に残る）/
  GmailApi（委任モード）= そのユーザーへのドメイン全体委任で送信（sub 切替）/
  GmailApi（ユーザー同意モード）= ユーザー単位トークンが登録されていれば本人のトークンで送信、
  無ければシステムトークン（Gmail が差出人を同意した本人に書き換える）
- DebugRedirectAllTo（誤送信防止）中も From は維持される（宛先だけ退避）
- 担当者への返信をさせたいだけなら `ReplyToVariable`（返信先=担当者・差出人はシステム）でも表現できる。
  承認の順番到達通知はこの形（差出人=システム + 返信先=申請者）

### プロバイダ（組み込み 4 種）

| Type | 実装 | 用途の目安 |
|---|---|---|
| `Smtp` | MailKit (MIT) に刷新。`System.Net.Mail.SmtpClient`（MS非推奨）は廃止 | オンプレ・社内メールサーバー。配信サービスのSMTP口にも繋げる |
| `GraphApi` | HttpClient 直（client credentials でトークン取得 → sendMail）。SDK は使わない | M365 圏の通知系（自社ドメインから送る）。Exchange Online のレート制限（毎分30通級）があるため一斉送信には不向き |
| `SendGrid` | HttpClient 直（/v3/mail/send）。SDK は使わない | 一斉送信・到達性が必要な外部向け配信。personalizations でネイティブバルク（1リクエスト1000宛先） |
| `GmailApi` | HttpClient 直（users/me/messages/send に raw MIME）。SDK は使わない。**ClientSecret の JSON の種類で認証モードを自動判別** | Gmail/Workspace 圏の通知系。送信上限 2000通/日級のため一斉送信には不向き。下の2モード参照 |

`GmailApi` の2モード:

- **ユーザー同意モード（管理者不要・個人の Gmail でも可）**: ClientSecret = OAuth クライアントの client_secret JSON（installed/web）、TokenSecret = 本人がブラウザで1回同意して得たリフレッシュトークンの JSON（`{"refresh_token":"..."}`）。**同意した本人として**送信する。動的 From は本人の Gmail に送信者エイリアス（Send As）がある場合のみ。
  注意: GCP の OAuth 同意画面が「テスト中」ステータスだとリフレッシュトークンが7日で失効する（本番公開または内部アプリにすること）。
  位置づけ: TokenSecret は「システム送信者」用（差出人省略時・ユーザートークン未登録時のフォールバック）。
  営業N人が各自の From で一斉送信する規模は、Salesforce/HubSpot と同じく配信インフラ側で解く
  （SendGrid のドメイン認証 + `AllowedFromDomains` + FromVariable = 人が増えても運用ゼロ）。

  **ユーザー単位トークン（差出人ごとに本人として送る）**: ユーザーモジュールに **GmailTokenField**
  （書き込み専用列・クライアントに返さない。入力欄はフィールド自身が持つ = 貼り付け or トークンJSONファイルの読み込み。
  空のまま保存で既存トークン維持、「登録を解除」で削除）を置き、`Mail.UserModuleName` /
  `UserEmailFieldName` と GmailApi インフラの `UserTokenFieldName` を設定すると、
  差出人アドレスでユーザーモジュールを検索し、登録があれば**その人のトークンで・
  その人として**送信する（本人の送信済みに残る。検索は MailUserStore = サーバー内部 SQL）。
  未登録は TokenSecret にフォールバック。トークンの取得は現状ヘルパスクリプト等で本人が同意して貼り付け
  （アプリ内「Gmail をつなぐ」ボタン = OAuth コールバック基盤は将来。1:1 メール用途）。
  **Gmail 専用**であることは意図的（他インフラは上位レイヤで解決するので不要:
  GraphApi = アプリケーション権限で任意ユーザーとして送れる / SendGrid = ドメイン認証 / Smtp = リレー）。
  誰が登録できるかは**そのモジュールの書き込み権限がそのまま効く**（本人だけが自分の行を編集できる設計にする）。

  **保存時の暗号化（`Mail.TokenEncryptionKey`）**: トークンはパスワードのようにハッシュ（一方向）にはできない
  ——送信に本物が必要なので可逆でなければならない——ため、列は **AES-GCM 256bit・ランダム nonce**で暗号化して保存する
  （保存形式 `v1:` + Base64(nonce|ciphertext|tag)。将来の方式変更はプレフィックスで読み分ける）。
  暗号化はサーバーでしかできない変換なので、`CustomizedModuleDataIO.AddAsync / UpdateAsync` から
  `GmailTokenHelper.ProtectGmailTokens(moduleDesign, data, key)` を base 呼び出しの前に呼ぶ
  （PasswordHashHelper と同じ流儀・同じ場所）。**鍵未設定でトークンを保存しようとするとエラー**にする
  （平文フォールバックは作らない）。読み取り側（MailUserStore）は暗号化されていない値を**使わない**
  （エラーログを出して未登録扱い = システムトークンにフォールバック）。
  方式はOSSで公開されるが、安全性は鍵だけに依存する設計なので問題にならない（PasswordHashHelper の PBKDF2 と同じ考え方）。
  **鍵はリポジトリ・デザインファイルに置かない**（appsettings / 環境変数 `Mail__TokenEncryptionKey`）。
  守れる範囲は DB のダンプ・バックアップ・レプリカ・SQL 経由の漏えいで、サーバー自体が奪われた場合は守れない
  （鍵の保管を Key Vault 等に変えたい場合はテンプレ側の呼び出しで鍵の取得元を差し替える）。
- **委任モード（Google Workspace の管理者設定が必要）**: ClientSecret = サービスアカウントの JSON キー。JWT RS256 → jwt-bearer 交換で、SenderMailAddress（委任ユーザー）や動的 From のユーザーに成り代わって送信。事前設定 = GCP で Gmail API 有効化＋サービスアカウント作成＋Workspace 管理コンソールで「ドメイン全体の委任」に gmail.send スコープを許可（特権管理者の操作）。全社員分を一括で許可したい企業向け。

- **SDK をパッケージに焼き込まない**（DBプロバイダと同じ方針）。GraphApi / SendGrid / GmailApi は素の REST（HttpClient・依存ゼロ）、Smtp の依存は MailKit のみ。SigV4 署名が必要な Amazon SES は対象外
- 大量送信の可否はインフラの性質。「一斉送信は SendGrid 系インフラを使う」ことをドキュメントで案内する
- Gmail は `Smtp` インフラでも送れる（Workspace の smtp-relay.gmail.com 推奨、または smtp.gmail.com:587＋アプリパスワード）。`GmailApi` は SMTP を塞がれた環境・委任でのユーザー成り代わりが必要な場合の選択肢

### IMailSender（公開・差し替え可能）

DbAccessor と同じ流儀で public にし、独自プロバイダ（社内メールGW等）を差し込めるようにする。

```csharp
public interface IMailSender
{
    //プロバイダ設定の一斉送信上限 (共通層が超過をエラーにするために見る)
    int MaxBulkCount { get; }

    Task<MailSendResult> SendAsync(MailMessage message);
    //テンプレ＋宛先ごとの差し込み変数。ネイティブバルクのあるプロバイダはそれにマップ、
    //無いプロバイダは共有テンプレエンジンで解決して逐次＋レート制御
    Task<MailSendResult> SendBulkAsync(MailTemplate template, List<MailBulkRecipient> recipients);
}

public class MailSendResult
{
    public int TotalCount { get; set; }
    public int SuccessCount { get; set; }
    public List<MailSendFailure> Failures { get; set; } = new(); // { To, Error }
    public bool IsSuccess => Failures.Count == 0;
}
```

- **部分失敗の報告は契約**。全成功/全失敗の bool では一斉送信に使えない
- `MailBulkRecipient` = { To, Cc, Bcc, Variables(差し込み変数名→値) }
- 一斉送信のリクエストは「共通部分（件名・本文の雛形・添付）＋宛先ごとの変数リスト」で運ぶ（解決済み全文1万通を運ぶと数十MBになるため。SendGrid の personalizations にそのままマップできる）。`MailBulkTemplate`（共通部分の箱）は IMailSender 契約専用で、ワイヤには乗らない（リクエストDTOはフラット。サーバーが詰め替える）

### 独自インフラの差し込み（テンプレの対応表が唯一の対応表）

**「送信先の呼び名 → `IMailSender`」の対応表はテンプレ（ユーザー可触コード）の `MailSenderTable` だけが持つ**。
製品はプロバイダ名も設定形式も知らないので、独自インフラ（社内メールGW・Amazon SES 等）を足すときは
`IMailSender` を実装して**この switch に1行足すだけ**（設定もそのアプリの appsettings に好きな形で置ける）。

```csharp
//「送信先の呼び名」→送信インフラ実装の対応表。独自インフラ(IMailSenderの実装)を使うときはここに1行足す
public static IMailSender? Create(string name, Func<string, Task<string?>>? gmailUserTokenResolver = null)
{
    var config = SystemConfig.Instance;   //プロバイダ設定は Program.cs がセクションごとに読んでいる
    return name switch
    {
        "GraphApi" => new GraphApiMailSender(config.GraphApi),
        "SendGrid" => new SendGridMailSender(config.SendGrid),
        "Gmail" => new GmailApiMailSender(config.Gmail, userRefreshTokenResolver: gmailUserTokenResolver),
        //呼び名の省略(空)はここに来る = このアプリの既定
        "Smtp" or "" => new SmtpMailSender(config.Smtp),
        _ => null,
    };
}
```

`MailDispatcher` はこの対応表（`Func<string, IMailSender?>`）を**必須の引数**として受け取る。
`null` が返れば「そのインフラは未設定」エラー。製品側に組み込みの switch は無い
（以前は製品とテンプレの2箇所に対応表があった）。

- ネイティブバルクの無い独自インフラの `SendBulkAsync` は `SmtpMailSender.CreateResolvedMessage`
  （テンプレ＋宛先1件→解決済みメッセージ。この用途のために public）で逐次送信する（GraphApi / GmailApi と同型）

### 誤送信防止（DebugRedirectAllTo）

- `Mail.DebugRedirectAllTo` が設定されていると、**全プロバイダ共通層で** To/Cc/Bcc をこのアドレスに差し替えて送る（開発・検証環境用）
- 元の宛先はメールヘッダ `X-CLB-Original-To` に記録（本文は改変しない）。3プロバイダともカスタムヘッダ対応
- 一斉送信時は宛先数分送らず、先頭 10 通のみ転送＋総件数をヘッダに記録（検証環境で1万通飛ばさない）

## 2. テンプレート解決エンジン（共有）

- 共有コード（クライアント/サーバー同一アセンブリ）に 1 実装。スクリプトのプレビュー・個別文面組み立てと、サーバーのバルク解決で同じ結果になる
- 構文（2026-08-09再改訂: **デザイン変数と同じ表記に統一**。Excel テンプレの `$Email.Value` や Variable の `"Id.Value"` と同じ言語感覚）:
  - トークンは `VariableName`（フィールドパス＋メンバー）として解釈。末尾セグメントが既知メンバー（`Value` / `DisplayText`）のときだけメンバー扱い
  - `{Name}`（メンバー省略）: **表示文字列**（Select/Link は表示名、数値・日付はフィールドの外部テキスト書式）
  - `{Name.Value}`: 値。Select/Link は**コード値**。数値・日付は外部テキスト書式で整形（メールはセル書式のないテキスト媒体のため。Excel との意味差は媒体差として割り切る）
  - `{Rank.DisplayText}`: 表示テキスト（Select/Link のみ。他は空文字）
  - `{Contact.Email.Value}`: **リンクパス**（Link/SelectField の参照先モジュールのフィールド）。リスト取得データが `"Contact.Email"` キーで持つ値をそのまま使う。サーバー解決経路 (MailBulkSearch / 承認の順番到達通知) では、宣言なしのリンクパスを `MailLinkPathLoader` がリンク先モジュールの一括ロード（バッチIN・多段は再帰）で解決して行へ注入する（データ層の SelectFields は宣言済みフィールドしか実体化しないため）
  - `{{` `}}` は `{` `}` のリテラル
- `EmailAddressVariable` / `OptOutVariable` も同じ表記（`"Email.Value"`、リンクパス可、末尾メンバー省略可）
- 組み込み変数は無し。レコードへのリンクはテンプレートに URL を直書きして `{Id.Value}` 等を混ぜる（例: `https://app.example.co.jp/Main/Contact/{Contact.Id.Value}`）。※`{RecordUrl}` と `Mail.AppBaseUrl` は 2026-08-23 に削除（直書きで代替できる糖衣に設定を1つ増やす価値がない・外部宛先はアプリにログインできずリンク先を開けないため）
- `IsBodyHtml=true` のとき差し込み値は HTML エスケープする（インジェクション防止）。テンプレ自体はエスケープしない（設計者が書くHTML）
- 差し込みコンテキスト: 単発送信＝渡した Module/ModuleData、一斉送信＝宛先行
- 存在しないフィールド名は空文字に解決（実行時に落とさない。テンプレはデータ由来のため静的検証はしない）
- リンクパスの書式整形（リンク先の日付書式等）はデザイン検索デリゲート（サーバー=DesignData、クライアント=AppInfoService）がある場合のみ。無い環境では ToString になるだけで解決自体は成立する

## 3. スクリプト API（MailField の値プロパティ）

（2026-08-24改訂: **Mail スクリプトオブジェクトは削除**。単発送信は MailField に一本化した。
MailField の各項目は「値」と「変数」のペアで、**値が入っていれば値、空なら変数を解決**する。
値はスクリプトから設定できるため、完全に動的な送信も MailField で行う。
旧経緯: 2026-08-09 に MailService → Mail オブジェクトへ改訂、BulkMail スクリプトオブジェクト削除=
一斉は BulkMailField に一本化・/bulk 経路廃止=宛先アドレスがクライアントに下りないことを構造で保証）

```csharp
//デザイン宣言どおりに送る
var result = ReceiptMail.Send();   //MailSendResult (IsSuccess/Failures)

//完全に動的な送信 (値プロパティをスクリプトで設定 = 変数より優先。メールインフラ名はデザイン固定)
ReceiptMail.To = "a@example.com;b@example.com"; //カンマ/セミコロン区切りで複数可 (Cc/Bcc も同様)
ReceiptMail.Subject = "承認依頼";      //値もテンプレートとして {変数} が自レコードで解決される
ReceiptMail.Body = "本文";            //HTMLは IsBodyHtml = true

var result2 = ReceiptMail.Send();     //履歴の SourceModule/SourceId は自レコード
```

- 一斉送信は BulkMailField（§8）。スクリプトからは `BulkMail1.Send()`（フィールドのスクリプトAPI）で起動できる
- 少数の宛先へのスクリプト送信（通知等）は MailField の値を差し替えながらループで（履歴は1通1レコード）
- BulkMail 削除で失うもの（承知の上の割り切り）: 一斉送信への添付（将来は BulkMailField に FileField 参照で回収）/
  キャンペーンレコードなしのアドホック一斉送信（履歴の起点も文面の記録も残らない運用なので v1 で塞ぐのはむしろ健全）/
  Preview（将来はフィールドの確認ダイアログに組み込み）
- 配線は `MailTransport`（static。エンドポイントURL2つ＋差し替え口 `IMailTransportHandler` 1つ）に集約。ハンドラは**HTTP POSTの置き換え**で、エンドポイントにPOSTするものと同じリクエストDTO（`MailSendRequest` / `MailBulkSearchRequest`）をそのまま受ける。リクエストDTOは**フラット**（Template入れ子なし。EmailAddressVariable/OptOutVariableはbulk_searchリクエストの持ち物）で、コントローラは `MailDispatcher.SendAsync(request)` / `MailBulkSearch.SendAsync(..., request)` に渡すだけの薄い形。デスクトップはこれを1クラス実装してセットする（HTTPを通さず MailDispatcher へ直結）。単発送信もクエリパラメータではなく `MailSendRequest`（MailInfraName=送信先の呼び名 ＋Message＋Source）をPOSTする。旧 `MailService`/`MailMessage`/`MailTemplate` のスクリプト公開は廃止（ワイヤ型として存続。MailMessageは純DTO）
- サーバーコードから宛先リストを組んで送る口は `MailDispatcher.SendBulkAsync(mailInfraName, template, recipients, source)`（公開）が引き続き存在する（承認フローフィールド等の将来のサーバー側利用者向け）

## 5. 送信履歴

**送信1回＝履歴モジュールに1レコード INSERT**。その回の失敗明細だけを JSON でひとつの列にまとめる（1万件送信の次の1万件は別レコード）。

- 履歴の有効化は**サーバー設定 `Mail.HistoryModuleName` を1つ**（Extras完結のためデザインデータ側ではなくappsettings。コアのAppSettings変更を避ける）。設定があれば**全送信**（単発・一斉とも）をサーバー側で自動記録、無ければ記録しない。送信のたびにスクリプトで指定はしない
- **フィールド名は履歴モジュールに置く契約フィールド（MailHistoryContractField）で解決**（2026-08-16 改訂。
  承認フローの契約と同じ「モジュールが契約を実装する」流儀。役割→フィールド名のリネーム自由・
  役割フィールドの存在をデザインチェックが検証・**空にした役割は記録しない**）。
  契約フィールドが無いモジュールには既定名（旧・予約名と同じ綴り）で書く:
  `SentAt`(DateTime) / `MailInfraName`(Text) / `Subject`(Text) / `TotalCount`(Number) / `SuccessCount`(Number) /
  `FailureDetails`(Text または JsonField。`[{"To":"...","Error":"..."}]`) / `SourceModule`(Text) / `SourceId`(Text)
- CreatedAt / Creator はシステムフィールドとして通常どおり自動
- **書き込みはサーバー内部経路**。送信操作したユーザーの履歴モジュールへの書き込み権限に依存しない（履歴はシステムの記録）
- 失敗明細の切り詰めはしない（1送信1レコードのため肥大は行単位で分散する）
- 明細の画面表示は `FailureDetails` 列を ListField データオーナーモード（DbColumn）で一覧化できる
- 検証は実行時（デザインチェックのアプリレベル拡張点がExtrasに無いため）: `HistoryModuleName` のモジュールが存在しない・予約名フィールドの型が不正な場合は送信時にエラーログ。送信自体は失敗させない（履歴は送信の従属機能）
- 内部書き込みの実装: コアに権限バイパスの公開書き込みAPIは無いため、アプリテンプレートの CustomizedModuleDataIO（protected AddAsync を持つ同梱ソース）に内部書き込み用の口を設け、MailService へ注入する

## 7.5 MailField（単発送信のフィールド化・2026-08-16 追加）

単発送信もデザインの一級市民にするフィールド（UI を持たない設定運搬 + スクリプト API `Send()`）。
宛先（変数 = リンクパス可 / 固定）・件名・本文テンプレート・送信者名をデザインで宣言し、
自レコードの値で `{変数}` を解決して送信する。宛先パスや変数はデザインチェックが検証し、
リネームに追従する（スクリプトの文字列組み立てでは得られない恩恵）。

使い分け: **MailField** = このレコードに紐づく単発送信 / **BulkMailField** = 名簿への一斉送信 /
完全に動的な送信も MailField の値プロパティで行う（Mail スクリプトオブジェクトは 2026-08-24 に削除）。
承認フローの通知連携（イベント→MailField 名のマッピングをサーバーフックが読む構想）は
このフィールドをテンプレート置き場として使う予定。

## 8. BulkMailField（ノーコードの一斉送信ボタン）

SFA のキャンペーン配信を想定した定型: **配信メール自体が1レコード**（件名・本文テンプレはただのフィールド＝データ）で、
宛先は同一モジュール上のリストフィールドを参照する。
**仕様は Salesforce（Campaign + CampaignMember + List Email）に寄せる**（後追いの利点=先行者の型をそのまま取る。オリジナリティ不要）:

- **宛先リストの行 = 送る対象そのもの**。「今回はこの人を外す」は行の削除（メンバーシップの操作）。
  除外フラグで名簿を汚さない（Salesforce でキャンペーン対象を外す＝メンバーを消す、と同じ）
- **配信停止（オプトアウト）は人の恒久属性**（Salesforce の Email Opt Out = `HasOptedOutOfEmail` 相当）。
  `OptOutVariable` がリンクパスで人側の Boolean を指し、送信時に常にスキップ（キャンペーンに関係ない最終安全弁）
- 運用フロー: キャンペーン作成 → 対象取込（条件検索→名簿へ一括生成。Salesforce の Add to Campaign 相当。
  v1 はスクリプトボタン/CSV取込/手動行追加）→ 精査（行の追加・削除）→ 保存 → 送信

```
メール配信 (MailCampaign)          … 1レコード = 1配信
├── Title (Text) / Body (Text複数行)   … テンプレート(データなので配信ごとに可変)
├── Members (DetailListField → 配信対象)  … 送る対象そのもの。または条件バインドの ListField
└── BulkMail1 (BulkMailField)
      RecipientListFieldName: Members / EmailAddressVariable: Contact.Email.Value
      OptOutVariable: Contact.メール拒否.Value (人側の配信停止=最終安全弁)
      SubjectVariable: Title.Value / BodyVariable: Body.Value / DbColumn: send_summary

配信対象 (CampaignMember)              … Salesforce の CampaignMember と同型
└── Campaign (Link) / Contact (Link → 担当者)   … 精査=行を足す/消す

担当者 (Contact)
└── Email (Text) / メール拒否 (Boolean)  … 配信停止は人に付く
```

- **送信は常に bulk_search（サーバー解決）経路**。リストの `GetSearchCondition()`（親バインド解決済み）から
  `LimitCount=null` で全件対象（画面のページング・列に縛られない）。宛先アドレスはクライアントに渡らない
- **未保存ガード**: `Module.IsNewData || IsModified` の間は送信不可（保存済み=サーバーから見える状態が送信対象。
  画面の未保存編集が「効いていないのに送れる」事故を防ぐ）
- 送信前に対象件数の確認ダイアログ。配信停止行・アドレス空行はサーバーでスキップ
- **送信結果サマリ**: `DbColumn` 設定時、`BulkMailSummaryEntry` の JSON 配列（新しい順・最大20件、失敗明細は先頭5件＋全数）を
  レコードの列へ**サーバー内部経路**（履歴と同じ `CustomizedModuleDataIO.UpdateSystemRecordAsync`＝protected UpdateAsync）で書き戻す。
  サマリ失敗は送信を失敗させない（ログのみ）。全量監査は従来どおり `Mail.HistoryModuleName`（任意）と二層
- `Source`（履歴の SourceModule/SourceId）はボタンが置かれたレコードで自動
- スクリプト API: `BulkMail1.Send()`（確認ダイアログ・トーストなしで送信し `MailSendResult` を返す）
- デザインチェック: リスト参照の存在/型、宛先変数（リンクパスは Link/Select の参照先を辿って最終フィールドまで検証）、
  テンプレ変数（自モジュール）、件名/本文の未設定。リネーム追従はリスト名・自モジュール変数・宛先モジュールの単純変数
  （リンクパスは既存のリンク越し変数と同じく非追従）
- デザイナ候補: EmailAddressVariable/OptOutVariable には `ModuleMember(SearchCondition.ModuleName)`＋`RelativeField(RecipientListFieldName)` を
  付与済み。ただし候補表示にはコアデザイナ側の RelativeField 対応（将来改修・未実装）が必要で、
  **現行デザイナでは候補なし=テキスト入力**（属性は null 安全に無視される）
- Salesforce から次に取るもの（将来）: **メンバー状態**（CampaignMemberStatus 相当。送信済み/失敗を名簿行へ書き戻し→失敗のみ再送）、
  対象取込の組み込み（Add to Campaign 相当・差分取込）、配信停止リンク・開封/バウンス Webhook（公開エンドポイント基盤待ち）
