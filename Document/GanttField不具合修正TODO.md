## 報告された不具合

### 1. 週のタイトルの先頭に「年」だけが出る

**状態**: 対応済み (`Fields/GanttTitle`、テスト `Test/Fields/GanttTitleTest`)。日・週・月のどの表示にも年を出す。月またぎ・年またぎの週は CalendarField と同じ形。月をまたぐ月表示 (幅に合わせない 42 日表示) は「2026年11月 - 2026年12月」。

日表示は曜日も出す (「2026年11月15日(日)」/「Sunday, November 15, 2026」)。日表示のヘッダーは時刻だけで、曜日がどこにも出ないため。書式はガント専用のリソース `DateFormatDayTitleWithWeekday` (CalendarField の日表示はヘッダーに曜日があるので変えていない)。

以下は対応前の調査内容。

**現象**: ツールバー左上が「年11月 15日 - 21日」になる (実画面で再現)。

**原因**: `GanttFieldComponent.razor` の `GetTitle()` が、リソース `WeekTitleSameMonth` の `{3}` (年) に空文字を渡している。

```csharp
_ when s.Month == e.Month => string.Format(Resources.WeekTitleSameMonth,
  s.ToString(Resources.DateFormatMonthNameFull, _culture), s.Day, e.Day, ""),
```

日本語リソースは `{3}年{0} {1}日 - {2}日` なので、年が空のまま「年」だけ残る。
英語リソース (`{0} {1} - {2}, {3}`) でも末尾に「, 」が残る。

**修正案**: CalendarField と同じく `s.Year` を渡す → 「2026年11月 15日 - 21日」。

**あわせて直したい点**: 同じ `GetTitle()` のほかの表示にも年が出ない。年をまたいで前へ / 次へ動かすと何年か分からない。

| 表示 | 今 | 修正後の例 |
|---|---|---|
| 日 | 11月15日 | 2026年11月15日 (`DateFormatDayTitle`) |
| 月 | 11月 | 2026年11月 (`DateFormatMonthTitle`) |
| 月またぎの週 | 11月29日 - 12月5日 | 2026年11月29日 - 12月5日 |
| 月 (FitToWidth でない 42 日表示) | 11月 - 12月 | 2026年11月 - 12月 |

CalendarField には年またぎ用の `WeekTitleDiffMonth` 系のリソースがあるので、同じものを使う。

**テスト**: タイトルの組み立てを Field 側の関数に寄せれば `Test/Fields/GanttViewStartTest` と同じ形で単体テストできる。

### 2. 開始 < 終了 のチェックが無い

**状態**: 対応済み (`Fields/GanttDateRange`、`GanttField.ValidateTaskAsync`、テスト `Test/Fields/GanttDateRangeTest`)。

- 判定: 日時は 開始 < 終了 (同じ日時も不可)、日付だけは 開始 <= 終了、どちらかが空なら見ない
- 比較は分まで。画面で入力する単位が分で、追加時の初期値に入っていた秒・ミリ秒のせいで「同じに見える日時」の判定が割れていた
- エラーは終了の項目の下に出す。文言は項目の表示名で組み立てる (「終了は開始より後にしてください。」)。通知は「入力エラー」(最初は文言をそのまま通知していた。3 の対応で、どの誤りでも「入力エラー」の 1 回にそろえた)
- 入れた場所は追加・更新の確定時だけ。下の修正案にある保存時 (`GanttField.ValidateInput()`) の検査は入れていない。DB に前後が逆の行が既にあると、原因が画面に見えないまま親の保存が毎回止まるため

以下は対応前の調査内容。

**現象**: 開始 11/18 10:00・終了 11/17 10:00 で OK を押すとそのまま通る。左のラベル行だけ出て、バーが描かれないタスクになる (実画面で再現)。

**原因**: チェックがどこにも無い。`GanttField.AddAsync` / `EditAsync` はダイアログのモジュールの `ValidateInput()` (各フィールド単体の検証) を呼ぶだけで、開始と終了の前後関係は誰も見ていない。

**修正案**: 開始・終了の項目を知っているのは GanttField なので、GanttField で比較する。

- 判定
  - DateTimeField: 開始 < 終了
  - DateField (日付のみ): 開始 <= 終了 (同日 = 1 日のタスクを許す)
  - どちらかが空のときは、この検査では何もしない (必須かどうかは各フィールドの `IsRequired` に任せる)
- 入れる場所
  - 追加・更新の確定時 (`AddAsync` / `EditAsync`)
  - 保存時の `GanttField.ValidateInput()` (ドラッグ・スクリプトで作られた行も拾う)
- エラーの見せ方: 終了フィールドに `SetError` でメッセージを出す (文言はリソースに追加。例「終了は開始より後にしてください」)

**補足**: バーのドラッグ (リサイズ) は `OnMouseMove` で既に逆転を防いでいる。

### 3. 進捗率 0 - 100 のチェックが無い

**状態**: 対応済み。案 A (`Fields/GanttProgressRange`、`GanttField.ValidateTaskAsync`、テスト `Test/Fields/GanttProgressRangeTest`) と案 B (Example の `GanttTask.Progress` に最小 0・最大 100) の両方を入れた。

案 A:

- 判定: Percent は 0 - 100、Ratio は 0 - 1。空なら見ない
- エラーは進捗の項目の下に出す。文言は項目の表示名と範囲で組み立てる (「進捗率は0から100の間で入力してください。」)
- 開始と終了の前後 (2) も誤りのときは、両方の項目にエラーを出す
- 入れた場所は追加・更新の確定時だけ (2 と同じ。保存時には入れていない)
- 実画面で確認済み (150 と -1 は閉じずにエラー、前後の誤りと同時に出る、100 は通る)

**進捗率が空のタスク** (2026-11-20 報告・対応済み): 範囲の検証は空を見ないので、進捗率が空のままタスクを作れた (表示は 0%)。次の 2 つを入れた。

- 追加時の進捗率の初期値を 0 にする (`GanttField.AddAsync`。空のときだけ入れるので、レイアウトの初期化のスクリプトが入れた値は残る)
- Example の `GanttTask.Progress` を必須にする (12 と同じ方法)。空で OK を押すと、閉じずに「必須項目です」が出る
- ガント自身は空を弾かない (進捗を空のままにしてよいかは設計者が決める。本体の数値フィールドに既定値の設定は無いので、必須にするデザインでは初期値の 0 が効く)
- 実画面で確認済み (写しのデザインで必須にして確かめた。初期値が 0、空は閉じずにエラー、0 は通る)
- DB に進捗率が空の行が既にあるとき、その行をガントのダイアログで更新するには値を入れる必要がある

**誤りを 1 回で全部出す** (2026-11-20 対応済み): `ValidateTaskAsync` は、各項目の検証 (必須など) が失敗するとそこで戻り、前後と進捗の範囲を調べていなかった。誤りが両方にあると、OK を 2 回押すことになっていた。各項目の検証が失敗しても続けて調べ、全部のエラーを 1 回で出す形にした。

- 同じ項目に各項目の検証のエラーが既にあれば、そちらを残す (ガントのエラーで上書きしない。案 B で進捗に最小・最大を入れると、進捗の範囲は本体のエラーが出る)
- 通知は、どの誤りでも「入力エラー」を 1 回だけ出す。具体的な内容は項目の下に出る。必須などは「入力エラー」、前後と進捗の範囲は文言そのまま、と分かれていたのをそろえた (CalendarField / TaskBoardField のダイアログも「入力エラー」の 1 つ)。実画面で確認済み
- 残る制約: 終了・進捗の項目がダイアログのレイアウトに置かれていないと、エラーの内容がどこにも出ない (通知は「入力エラー」だけ)。置いていない項目は入力もできないので、追加時の初期値 (前後が正しい・進捗 0) のままなら誤りにならない
- 実画面で確認済み (タイトルが空 + 進捗率 150 + 終了が開始より前 で、3 つのエラーが 1 回で出る)

**案 B** (2026-11-20 対応済み): `GanttTask.mod.json` の Progress に `"Min": 0, "Max": 100` を足した。実画面で確認済み (写しのデザイン)。

- 入力欄 (`<input type="number">`) に min / max が付く
- ガントのダイアログ: 150 は「最大値より大きい値です」、-1 は「最小値より小さい値です」(本体の文言) で閉じない。通知は「入力エラー」。100 は通る
- タスクの詳細ページ (`/Main/GanttTask`): 150 で保存すると同じエラーで保存されない。通知は本体の「不正な入力があります」
- 詳細ページから新規に作るときの進捗率の初期値は空 (初期値の 0 はガントの「+ 追加」だけ)。必須なので、空のままでは保存できない

A と B を両方入れる理由: A はガントのダイアログにしか効かない。B を入れると、タスクの詳細ページでも範囲が効く。B を入れたあとの Example では、進捗の項目に本体の検査のエラーが出てそちらを残すので、A の文言は画面では見えなくなる (A はデザインに最小・最大が無いときの備え)。

以下は対応前の調査内容。

**現象**: 150 がそのまま入る。ラベルは「100%」と表示されるが、値は 150 のまま保存対象になる (実画面で再現)。

**原因**: Example の `GanttTask.Progress` (NumberField) に最小・最大が設定されていない。描画された `<input type="number">` にも min / max が無い。GanttField は表示のときに丸めるだけ (`ProgressScale.ToFillPercent`)。

**修正案** (どちらか、または両方):

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A | GanttField が `ProgressScale` に応じた範囲を検査する (Percent: 0 - 100、Ratio: 0 - 1) | デザインの設定漏れに依存しない。Ratio にも正しく効く | フィールドの責務が少し増える |
| B | Example のデザインで Progress に最小 0・最大 100 を設定する | コード変更なし | 利用者のデザインでは同じ漏れが起きる |

**推奨**: A (入れる場所とエラーの見せ方は 2 と同じ = `GanttField.ValidateTaskAsync` に足し、進捗の項目の下にエラーを出す)。Example は B も入れておくと、入力欄の時点で範囲が効く。

**本体の確認結果**: `NumberFieldDesign` に `Min` / `Max` (`decimal?`) があり、`NumberField.ValidateInput()` が範囲外をエラーにする (メッセージは本体のリソース)。案 B は `"Min": 0, "Max": 100` を足すだけで効く。

### 5. 色の #000000 が既定値のように見える

**現象**: 色を触らずにタスクを追加すると、ピッカーは黒 (#000000) を表示しているのに、バーは既定の青 (#1a73e8) で描かれる (実画面で再現)。

**原因**: ColorPickerField は値が空のとき `Design.Default` (既定 `#000000`) を**表示するだけ**で、値には入れない。

```razor
private string DisplayValue => string.IsNullOrEmpty(Field.Value) ? Field.Design.Default : Field.Value!;
```

値は空のままなので、GanttField は「色の指定なし」と見てデザインの `BarColor` → CSS の既定色を使う。

**副作用**: ピッカーが最初から #000000 を指しているので、黒を選んでも変更イベントが起きず、黒を設定できない。一度別の色を選んでから黒に戻す必要がある。

**修正案** (ColorPickerField の仕様変更になるので、どちらかを選ぶ):

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A | 「未設定」を状態として見せる。値が空なら「未設定」と表示し、設定済みならクリアボタンを出す | ガントの「空 = フィールドの既定色」と合う。黒も選べる | UI の追加が要る。`Default` の意味 (未設定時の見本色) を docs に書き直す |
| B | 新規レコードで `Default` を実際の値として入れる | 見た目と値が一致する | 既定のままだと全タスクが黒で始まる。既存の空の行は直らない |

**推奨**: A。Example は加えて `BackgroundColor` の `Default` を空かガントの既定色 `#1a73e8` にする。

**影響範囲**: ColorPickerField を使うほかの画面 (ProgressField の `ColorField` など) も同じ動きになる。docs/ColorPickerField.md の更新が要る。

### 6. 入力エラーで編集内容が消える

**状態**: GanttField は対応済み (`AddAsync` / `EditAsync`)。エラーのときは同じモジュールでダイアログを開き直すので、入力した内容と各項目のエラーが残る。いったん閉じてから開き直す作りなので、一瞬ちらつくことがある。CalendarField / TaskBoardField / MarkerListField は未着手。

以下は対応前の調査内容。

**現象**: ダイアログで入力エラーになると、「入力エラー」の通知だけ出て編集内容が破棄される。どの項目が悪いかも見えない。

**原因**: ダイアログを閉じた**後**に検証している。

```csharp
if (await mod.ShowDialogAsync(OK, Cancel) != OK) return;
if (!await mod.ValidateInput())
{
    await Services.UIService.NotifyError(Properties.Resources.InputError);
    return;
}
```

**修正案**: エラーのときは同じモジュールでダイアログを開き直す (各フィールドのエラー表示が残った状態で直せる)。2・3 の検証を入れるとエラーになる場面が増えるので、同時に直したい。

**範囲**: CalendarField / TaskBoardField / MarkerListField も同じ作り。共通の部品 (`OwnedRecordModules` あたり) に寄せて 4 フィールドまとめて直すか、今回は Gantt だけにするかを決める。

**本体の確認結果**: `Module.ShowDialogAsync` は押されたボタンの文字列を返すだけで、`DialogButton` にも「閉じる前に検証する」口は無い。Extras 側で開き直す形にする。

### 8. 追加時の初期値が現在時刻

**状態**: 対応済み (`GanttDateRange.GetDefault`、テスト `Test/Fields/GanttDateRangeTest`)。初期値は、見えている期間 (`GetViewDateRange`) に今日があれば今日、無ければ期間の最初の日の 1 日ぶん。DateTimeField は その日の 0:00 〜 翌日の 0:00、DateField は 開始 = 終了 = その日 (1 日のタスク)。半端な時刻・秒より下の端数は入らなくなった。

14 (基準日の強調) を入れたあとは、初期値の日を基準日から決める形に見直す (18)。

以下は対応前の調査内容。

**現象**: 「+ 追加」の初期値が、開始 = 現在時刻 (例 14:27)、終了 = その 1 日後になる。

### 15. 「横幅に収める」がオフのとき、週が 14 日・月が 42 日になる

**状態**: 未着手。表示する日数を決める。

**現象**: 「横幅に収める」(`FitToWidth`) がオフ (既定) のとき、週表示は 14 日ぶん、月表示は 42 日ぶんを表示する。オンのときは週 = 7 日、月 = その月の日数。

```csharp
return (ViewMode, Design.FitToWidth) switch
{
    (GanttViewMode.Day, _) => (start, start.AddDays(1)),
    (GanttViewMode.Month, true) => (start, start.AddMonths(1)),
    (GanttViewMode.Month, false) => (start, start.AddDays(42)),
    (_, true) => (start, start.AddDays(7)),
    _ => (start, start.AddDays(14)),
};
```

**経緯**: 最初のコミット (2026-03-01「GanttChart追加」) からこの数で、理由は残っていない。42 日はカレンダーの月表示 (6 週 × 7 日) の数と同じ。カレンダーは 6 行の格子を埋めるために 42 日が要るが、ガントは日が横に並ぶだけなので、42 日にする理由は無い。

**困ること**:

- 「月」なのに翌月の 11 日前後まで見える。「週」なのに 2 週間見える
- 前へ / 次へ は 1 か月 / 1 週間ずつ動くので、表示が毎回重なる (11 月の表示に 12/1 - 12/12 が出て、次へ を押すと 12/1 から始まる)

- 「横幅に収める」のオン / オフで表示する期間が変わる。この設定は幅の決め方のはずで、期間まで変わるのは名前から読み取れない

**修正案**: 「横幅に収める」に関係なく、週 = 7 日、月 = その月の日数にする。オフのときは今までどおり 1 列の幅を固定し、入りきらなければ横にスクロールする。

**検討すること**:

- 既存の利用者には見える期間が短くなる変更になる (週 14 日 → 7 日、月 42 日 → 28 - 31 日)。リリースノートに書く
- 「先まで見たい」使い方には、期間指定 (CustomRange) を案内する
- 月表示の列幅は 32px。31 日で約 1000px なので、広い画面では右に余白が出る。余白のままにするか、幅が余るときは広げるか
- タイトルの「月をまたぐ月表示」の分岐 (`GanttTitle.Month`) は、スクリプトで `ViewStart` に月の途中の日を設定したときに残る (その日から 1 か月ぶん)。週も同じ
- テスト `Test/Fields/GanttViewStartTest` / `GanttTitleTest` に 14 日・42 日を前提にしたものがあれば直す。docs/GanttField.md の「ツールバーのタイトル」の最後の 1 文も直す

**影響する箇所**: `GanttField.GetViewDateRange` (読み込む範囲・タイトル・ドラッグの換算がここを使う)。

### 16. 期間指定の終了日が、指定した日の前日までになる

**状態**: 未着手。終了日を含めるかどうかを決める。

**現象**: 期間指定で 終了 = 2026/12/31 にすると、タイトルは「2026年1月1日 - 2026年12月30日」になり、12/31 は表示されない。ポップアップを開き直すと終了は 12/31 と出るので、タイトルと 1 日ずれて見える (実画面で再現。Example のボタンのスクリプト `SetCustomRangeAsync(2026/1/1, 2026/12/31)` と、ポップアップからの指定の両方)。

if (ViewMode == GanttViewMode.CustomRange)

日 / 週 / 月の範囲は「開始 以上・終了 未満」で持っていて、期間指定も同じ形に入れている。利用者が入れる「終了」は、その日まで見たい日のはずなので、意味が合っていない。

- 開始 = 終了 (1 日だけの期間) を許すことになる。9 のポップアップの検証は 開始 <= 終了 に変える (日付だけの判定 = `GanttDateRange` の isDateOnly と同じ)
- 既存の利用者には、表示が 1 日ぶん増える変更になる。スクリプトで終了に「翌日」を渡して合わせているデザインがあれば、1 日多く出る
- docs/GanttField.md の `SetCustomRange(start, end)` に、終了日を含むことを書く

**影響する箇所**: `GanttField.GetViewDateRange`、`GanttFieldComponent.ApplyRangePopup`。

### 17. 期間指定のポップアップで、存在しない日付を打つと黙って前の日付が使われる

**状態**: 未着手。コードから分かった原因で、実画面での再現は報告のみ (2026-11-19)。

**現象**: 期間指定のポップアップで、開始か終了に「2026/11/31」のような存在しない日付を手入力して OK を押すと、エラーにならずに閉じる。適用される期間は、その欄だけ打つ前の日付のまま。画面に出ていた日付と違う期間が、何も言わずに適用される。欄を空にして OK を押したときも同じ。

**原因**: 存在しない日付のとき、ブラウザの `<input type="date">` は見た目に打った文字を残したまま、値として空を返す。`GanttFieldComponent` の `@onchange` は、日付として読めない値を無視して前の値を持ち続ける。

```razor
@onchange="e => { if (DateTime.TryParse(e.Value?.ToString(), out var d)) _rangeEditStart = d; _rangeError = null; }"
```

`ApplyRangePopup` は持っている値 (打つ前の日付) で前後を判定するので、それが正しければ閉じる。9 で足したのは開始と終了の前後の判定だけで、読めない入力は見ていない (9 より前からある動き)。

**修正案**: 欄ごとに「読めない値が入っている」ことを覚え、OK で閉じずにその欄を赤枠にしてエラーを出す (文言は新しいリソース。例「日付が正しくありません。」)。正しい日付を入れ直したら消す。開始・終了のどちらの欄にも出せるように、赤枠は欄ごとに持つ (今は終了の欄だけ)。

**影響する箇所**: `GanttFieldComponent` の期間指定のポップアップ (`@onchange`・`ApplyRangePopup`・`OpenRangePopup`)、`Properties/Resources*.resx`。

### 18. 追加時の初期値を基準日から決める (8 の見直し)

**状態**: 未着手。14 を入れたあとに行う (2026-11-20 追記)。

**案**: 日 / 週 / 月 の表示では、追加するタスクの初期値を基準日にする。今 (8) は「見えている期間に今日があれば今日、無ければ期間の最初の日」。

**理由**:

- 基準日は必ず見えている期間に入る (日 / 週 / 月 のどれでも、スクリプトで `ViewStart` を設定したあとでも)。足したタスクが画面に現れる、という 8 の目的はそのまま満たす
- 14 で基準日が見える (選べる) ようになると、「色の付いた日に追加される」と説明できる。規則が 1 つになる (今日か最初の日か、の分岐が無くなる)
- 初期表示と「今日」ボタンの直後は基準日 = 今日なので、今と同じ結果になる

**今と変わる場面**:

| 場面 | 今 (8) | 変更後 |
|---|---|---|
| 今日が見えているが、基準日は今日ではない (スクリプトで `ViewStart` を設定した・14 でヘッダーの日付を選んだ・14 日 / 42 日の表示で 前へ を押しても今日が残っている) | 今日 | 基準日 |
| 今日が見えていない (前へ / 次へ で別の週・月へ動いた) | 期間の最初の日 (週 = 日曜、月 = 1 日) | 基準日 (動かす前と同じ曜日・同じ日) |

**14 を先にする理由**: 基準日が見えないまま変えると、2 行目の場面で「なぜこの日に追加されるのか」が画面から分からない。

**決めること**:

- 時刻と長さは 8 のまま (日時 = 基準日の 0:00 〜 翌日の 0:00、日付だけ = 開始 = 終了 = 基準日)
- 期間指定 (CustomRange) は基準日を出さない (14) ので、今の規則のまま (今日があれば今日、無ければ期間の最初の日) にする。期間指定の基準日は、初期表示では今日、`SetCustomRange` のあとは開始日で、そろっていない
- 14 でヘッダーの日付のクリックを入れない場合も変えるか (基準日が見えるだけでも説明はつく。クリックで選べると「追加したい日を選んでから追加」ができて、変える意味が大きい)

**影響する箇所**: `GanttField.AddAsync` (基準日を渡す。`_baseDate` は private のままでよい)、`GanttDateRange.GetDefault` (日 / 週 / 月 は基準日・期間指定は今の規則)、テスト `Test/Fields/GanttDateRangeTest`、docs/GanttField.md と CLAUDE.md の初期値の説明。
