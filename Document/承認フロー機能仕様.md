## 目的とポジション

> 業務アプリに ApprovalFlowField を 1 つ置けば、日本企業で必要な本格稟議が動く。必要なら C# / Script / API で深く拡張できる。

- 狙う位置: **kintone / Power Apps より承認が強く、intra-mart / Appian より圧倒的に組み込みが簡単**
- 現行の PatternShowcaseAuth テンプレート（7モジュール＋スクリプト430行コピー）を製品組み込みに昇格させる
- BPM 製品は目指さない（完全 BPMN・サブプロセス・自由接続は対象外）

## 層構造（この機能の見取り図）

承認フローの仕様はアプリごとに大きく異なりうる。そのため「共通で使える部分」を層で切り、
**上の層ほど差し替え可能**にする。

```
L1 サーバー（ApprovalEngine + command API）… 不変。資格・版・遷移の整合と履歴の不変性だけを強制する
L2 スクリプト API（承認.Approve / Reject / SubmitWithRoute / FlowStatus …）… どの UI からでも呼べる
L3 標準 UI（フィールド内蔵のステッパー・ボタン・コメント・履歴）… 高確率で使えるデフォルト。
   Show* プロパティで部分的に、ShowActions=false で丸ごと退かせられる
L4 カスタム UI … 通常のローコード。承認データはただのモジュールなので ListField / DetailList で表示し、
   ButtonField ＋ スクリプト API で操作を作れる。UI を丸ごと作り替えても L1 の検証は同じに効く
```

### 「決めすぎない」原則

- **エンジン (L1) が強制するのは安全性の不変条件だけ**: 本人・承認者の資格、expectedVersion、
  遷移の整合、履歴の不変性
- **業務ポリシーはデザインで可変**: 取り下げの許可範囲 (WithdrawPolicy)、コメント必須、完了条件、
  編集ロックの範囲 (DataWriteCondition = 元からアプリの手の中)
- **UI の挙動 (アクション後の画面更新等) は UI 層の責務**: 標準 UI は無難なデフォルト
  (フィールド表示の再読込) を持つだけ。それ以上の画面更新が要るアプリはボタンを外付けにして
  自分のスクリプトで行う (専用の状態変化フックは持たない)

## 全体アーキテクチャ

```
申請書モジュール（ユーザー定義・複数可）
  └ ApprovalFlowField（UI: ステッパー・ボタン群・コメント・履歴 ＋ FK列 ＋ 経路定義）
        │  クライアントは表示と command API 呼び出しのみ
        ▼
command API（Extras.Server の Controller。状態遷移の唯一の口）
  Load → Authorize → Validate State → Validate Version → Apply
  → History → Activate Next → Commit → Notify(Outbox)
        │  システム権限書き込み（操作ユーザーの権限を通さない）
        ▼
承認データモジュール（自動生成・全申請書モジュールで共有）
  必須:      ApprovalFlow / ApprovalFlowMember / ApprovalHistory   … 3つ
  オプション: ApprovalNotification（通知Outbox）/ ApprovalDelegation（代理）
            / 経路マスタ 3つ（エンドユーザーが経路を画面管理したい場合のみ）
        │
        ├─ メンバー解決（下層機能）… 申請時に承認者を実ユーザーへ解決しスナップショット
        ├─ MailDispatcher … Outbox ワーカー（IHostedService）が送信・リマインド
        └─ 権限連携 … 申請書の DataWriteCondition が編集ロック（サーバー強制）
```

### 段階構成（小さく始めて必要なら育てる）

| 構成 | モジュール数 | できること |
|---|---|---|
| 最小 | **3**（Flow / Member / History） | 固定経路（デザイン定義）の承認・却下・差し戻し・履歴・承認待ち一覧 |
| 標準 | 4（＋Notification） | ＋メール通知・リマインド |
| フル | 8（＋Delegation＋経路マスタ3） | ＋代理承認・エンドユーザーによる経路管理 |

### 基本方針（決定事項）

1. **承認データはユーザープロジェクトのモジュール**。エンジンは生 SQL を書かない。
   ただしユーザーが手で作るのは非現実的なので**デザイナ/CLI が自動生成する**（§8。実装は後日で仕様のみ確定）。
   生成後は通常のモジュールなので、フィールド追加・画面カスタムは自由
2. **全申請書モジュールで同じ承認モジュールを共有する**のが標準（§8）。承認待ち一覧が 1 検索で全申請種別を横断できるのはこの共有が前提。
   インスタンス行は `TargetModuleName` / `TargetId` で申請書と紐づく
3. **結合は明示指定＋デフォルト名**。エンジンが使うモジュール名・フィールド名はすべて ApprovalFlowField の
   デザインプロパティで指定する（§4。デフォルト名充填済み。自動生成が設定するのでユーザーは通常触らない）。
   綴り一致の暗黙予約名は不採用（明示参照ならリネームリファクタ追従・デザインチェック・候補表示の既存機構に乗る）
4. **経路定義は 3 ソースの選択制**（§3）。メンバーの決め方で選ぶ:
   ルールベース（上長・役職）で経路が安定するアプリは**デザイン定義**、名指し運用で経路が人事とともに動くアプリは
   **UI 管理（経路マスタモジュール）**、申請内容に応じてその場で組む場合は**スクリプト組み立て**。
   どのソースも同じ中間表現に落ち、サーバーで解決・スナップショットされる（以降の扱いは完全に同一）
5. **状態遷移はサーバーの command API のみが行う**。承認系モジュールは UserWriteCondition で一般ユーザーの
   書き込みを封じ（既定: 誰も不可）、エンジンはシステム権限で書く
6. **申請時スナップショット**。経路・承認者は申請時に解決して Member 行へ複製する。
   進行中の申請は経路改定・人事異動の影響を受けない → 経路バージョン管理は不要（v1 の割り切り）
7. **core 無改変**。Extras＋App テンプレートへの結線数行で成立（2026-08-13 core API 調査で確認済み）

## 2. 状態遷移

```
（未申請: フロー行なし）
   │ Submit
   ▼
InProgress ──最終ステップ完了──▶ Completed
   │  │  │
   │  │  └─Reject──▶ Rejected ──Resubmit──▶ InProgress(AttemptNo+1)
   │  └─Return(申請者へ)──▶ Returned ──Resubmit──▶ InProgress(AttemptNo+1)
   └─Withdraw(申請者。許可範囲は WithdrawPolicy: 既定=承認が始まる前のみ / Anytime)
      ──▶ Withdrawn ──Resubmit──▶ InProgress(AttemptNo+1)

※「取消」状態は持たない。完全にやめたい場合は取り下げ (Withdraw) 後にレコードを削除する
  (取り下げ状態は編集ロックが解けるため通常のレコード削除が可能)。
※進行中 (InProgress) を離れる遷移 (却下・申請者への差し戻し・取り下げ) では、残りの
  Waiting メンバーを Skipped にする (承認待ち一覧に処理できない行を残さない)。
```

- **ステップは Member 行の StepNo グループとして表現**する。ステップの完了・現在位置は
  「StepNo 昇順に、未完了の最初の Approval ステップが現在」をエンジンが計算する（CurrentStepNo はその写し）
- ステップ完了判定（CompletionPolicy）:
  - `RequiredMembers`: 必須全員承認（必須ゼロなら任意 1 人）— 現行テンプレート互換・既定
  - `All`: 全員 / `Any`: 1 人
  - k/n 定足数・割合は v2
- `Confirmation` ステップは**フローをブロックしない**（到達と同時に次ステップへ進行。メンバーは Confirm を記録できる。
  未確認でもフローは完了しうる）。ブロックする確認が必要なら StepType=Approval を使う
- `Return`（差し戻し）: ReturnScope に従い申請者（既定）または過去の任意ステップへ。
  ステップへの差し戻しは対象〜現在の Member を Waiting に戻す。フロー状態は InProgress のまま
- `Resubmit`: 経路を**再解決**する（申請内容の変更で条件分岐・承認者が変わりうるため）。
  旧 Member 行は削除せず AttemptNo で世代を分けて残す（履歴と整合）
- 自己承認: SelfApprovalPolicy に従う。`Skip` = 申請者に解決されたメンバーを Skipped で生成
  （ステップが空になる場合はステップごとスキップ）。`Deny` = 申請時にエラー

## 3. 経路定義（3 ソース）

どのソースで定義しても、エンジンは同じ中間表現（ルート＝ステップ列＋メンバールール）を受け取り、
**サーバーでメンバー解決 → Member 行へスナップショット**する。以降の状態遷移・権限・通知はソースに依存しない。

| ソース | 向いている運用 | 経路の変更手段 |
|---|---|---|
| Design（デザイン定義） | ルールベース（上長・役職・グループ）で経路が安定するアプリ | デザイン配布 |
| Modules（UI 管理） | 名指し運用・部門別経路など、管理者が実行時にメンテするアプリ（現テンプレートと同じ運用） | 管理画面 |
| Script（その場組み立て） | 申請内容・画面操作に応じて経路を動的に組むアプリ（申請者による承認者指定を含む） | スクリプト |

### Design ソース

経路を **ApprovalFlowField のデザインプロパティとして定義**する（kintone のプロセス管理と同じ「アプリ設計の一部」）。

```csharp
public class ApprovalRouteDesign          // フィールドの Routes コレクションの要素
{
    public string Name { get; set; }
    public SelfApprovalPolicy SelfApprovalPolicy { get; set; } = Allow;  // Allow / Skip / Deny
    public List<ApprovalStepDesign> Steps { get; set; }
}
public class ApprovalStepDesign
{
    public string Name { get; set; }                       // 例: 課長承認
    public ApprovalStepType StepType { get; set; }          // Approval(既定) / Confirmation
    public CompletionPolicy CompletionPolicy { get; set; }  // RequiredMembers(既定) / All / Any
    public bool IsCommentRequiredOnReject { get; set; } = true;
    public ReturnScope ReturnScope { get; set; }             // ApplicantOnly(既定) / AnyPreviousStep
    public int? ReminderAfterDays / ReminderIntervalDays / ReminderMaxCount { get; set; }
    public string ConditionFieldName { get; set; }           // 実行条件（1 個。空 = 常に実行）
    public MatchComparison ConditionComparison { get; set; }
    public string ConditionValue { get; set; }
    public List<ApprovalStepMemberDesign> Members { get; set; }  // ResolverType / ResolverValue / IsRequired
}
```

- デザイナのコレクションエディタで編集。デザインチェック・リネーム追従の対象
- 経路の変更 = デザイン配布。進行中の申請はスナップショット済みなので影響なし
- 経路マスタ 3 モジュールは不要（最小 3 モジュール構成が成立する理由）

### Modules ソース

エンドユーザー（管理者）が実行時に経路を画面で管理するアプリ向け。経路マスタ 3 モジュール（§1）を使う。
現行テンプレートの経路テンプレート管理と同じ運用で、名指し運用（人事とともに経路が動く）の主経路。

- ステップ・条件・メンバーの表現力は Design ソースと同一
- メンバー行の編集は **MemberRuleField**（メンバー解決仕様 §6。型に応じたエディタを持つ複合フィールド）。
  管理画面は自動生成する標準画面（通常のモジュール画面なのでカスタム自由）
- ビジュアル経路エディタ（ドラッグで経路を組む専用フィールド）は v2 の磨き込み

### Script ソース（その場組み立て）

申請書モジュールのスクリプトが**申請時に経路を組み立てて渡す**。申請者による承認者指定・画面操作による動的経路の一般形。

```csharp
// ApprovalFlowField のスクリプト API（フィールド名が 承認 の場合）
var route = 承認.NewRoute();
var step1 = route.AddStep("上長承認");
step1.AddMember(MemberRule.Manager(1), true);            // ルール（解決はサーバー）
var step2 = route.AddStep("経理確認");
step2.StepType = "Confirmation";
step2.AddMember(MemberRule.User(承認者選択.Value), true); // 名指し（画面で選ばせた値）
承認.SubmitWithRoute(route);                              // 申請（経路同梱）
```

- スクリプトが組むのは**ルール（宣言）**であり、実ユーザーへの解決は常にサーバーの MemberResolver が行う
- 信頼モデル: スクリプト経路はクライアント由来のため「申請者が経路を指定できる」ことと等価
  （競合製品の「申請時の経路編集」と同じ性質の業務機能）。専用の許可フラグは置かない —
  スクリプトを書くこと自体がデザイナの意思であり、誰がどの経路で申請したかは履歴に不変記録される。
  申請後の遷移はソースに関わらずサーバー強制

### 経路の選択（Design / Modules 時）

| RouteSelectionMode | 動作 |
|---|---|
| `Fixed`（既定） | RouteName で 1 本を指定（Design ソースなら Routes の先頭を既定） |
| `ByField` | 申請書のフィールド値（RouteNameField で指定）をルート名として選択。現行テンプレートの「スクリプトでテンプレ名を返す」の置き換え |

Script ソースは選択の一般形でもある（RouteName を選んでマスタ経路をベースに加工する API も用意: `承認.LoadRoute(name)` → 編集 → `SubmitWithRoute`）。

## 4. ApprovalFlowField（デザインプロパティ＝明示指定）

エンジンが触る名前の解決は**各承認モジュールに置く契約フィールド**（§4.1）へ移した（実装済）。
ApprovalFlowField 側で指定するのはフローモジュール名だけで、メンバー・履歴モジュールは
フロー契約の Members / Histories 一覧の参照先として決まる。
未実装のモジュール群（通知・代理・経路マスタ）のマッピングは従来案のまま表に残す。

| プロパティ群 | 内容 |
|---|---|
| Routes / RouteSelectionMode / RouteName / RouteNameField | 経路定義と選択（§3） |
| WithdrawPolicy | 取り下げの許可範囲（BeforeFirstApproval=既定 / Anytime。業務ポリシー） |
| OnBuildRoute | 経路を組み立てるスクリプト（ApprovalRouteData を返す。設定すると組み込みの申請・再申請ボタンと Submit()/Resubmit() が使える） |
| FlowModuleName | フローモジュール名（既定 "ApprovalFlow"）。指定はこれ1つだけ。メンバー・履歴モジュールはフロー契約の Members / Histories 一覧の参照先として自動解決（実装済） |
| (移動: FlowModule / MemberModule / HistoryModule のマッピング) | 役割→フィールド名のマッピングは、申請書側のネスト設計オブジェクトではなく**各承認モジュールに置く契約フィールド**（§4.1）へ移した（実装済）。「モジュールが契約を実装する」形になり、複数の申請書からのマッピング重複宣言が消える |
| NotificationModule | ModuleName=""（空 = 通知 OFF）＋ 役割→フィールド名 |
| DelegationModule | ModuleName=""（空 = 代理 OFF）＋ 役割→フィールド名 |
| RouteModules | Route / RouteStep / RouteStepMember の ModuleName ＋ 役割→フィールド名（空 = Design モード） |
| OrganizationBinding | メンバー解決仕様 §2 の組織バインディング（Manager / Department / Position / MailAddress …） |
| NotificationTemplates | イベント別の件名/本文テンプレート（VariableName 表記。既定文面同梱） |
| ShowProgress / ShowHistory / ShowComment / ShowActions | 標準 UI の表示切り替え（ShowActions=false でボタン群を丸ごと退かせ、カスタム UI に置き換えられる） |
| DbColumn | FK 列（ModuleField と同様） |
| (廃止: StateDbColumn / ApplicantDbColumn) | コピー列は廃止し**フロー行への参照**に一本化した。状態はフローの `Status`、申請者はフローの必須フィールド `Applicant`（申請時にエンジンが書き込む LinkField）が正で、条件は**リンク越しスカラー参照**（コアの宣言なしドットパス）で `承認.Status.Value == null(未申請 = フロー行なし)` / `承認.Applicant.Value == CurrentUser` のように書く。申請書自テーブルの列は FK 1本だけになり、エンジンの親レコード書き込みも申請時の FK 設定 1 回だけになった。クライアント側の権限表示には申請書詳細レイアウトの DataOnlyFields に `承認.Status` / `承認.Applicant` / `承認.Members` を登録する |
| (廃止: MembersListFieldName) | 承認メンバー一覧は申請書側ではなく**フローモジュールの必須フィールド `Members`**（メンバーモジュールを `Flow == Id` で表示する ListField）に一本化した。条件エディタの「現在の承認待ち」「最終承認の番」は `(フィールド名).Members.～` の**リンク越し存在条件**（コアのリンク越しList参照）として組み立てる。申請書モジュールごとの一覧フィールド複製は不要。クライアントの権限表示には申請書詳細レイアウトの DataOnlyFields に `(フィールド名).Members` を登録する（§5） |

- モジュール名・フィールド名の参照はリネームリファクタの参照収集（CollectReference）に登録し、リネームに追従させる
- 同じモジュール群を指す複数の ApprovalFlowField（複数の申請書）はフローモジュール名を指すだけで、共有に特別な設定は不要

### 4.1 契約フィールド（インターフェイス。実装済）

各承認モジュールに契約フィールドを1つ置き、「役割 → 自モジュールのフィールド名」を宣言する:

| モジュール | 契約フィールド | 役割 |
|---|---|---|
| フロー | ApprovalFlowContractFieldDesign | Status / TargetModuleName / TargetId / RouteName / Applicant / AttemptNo / CurrentStepNo / Members / Histories |
| メンバー | ApprovalMemberContractFieldDesign | Flow / AttemptNo / StepNo / StepName / StepType / CompletionPolicy / IsCommentRequiredOnReject / ReturnScope / ApproverUser / IsRequired / IsFinalStep / Status / ActedAt |
| 履歴 | ApprovalHistoryContractFieldDesign | Flow / AttemptNo / StepNo / Action / ActorUser / FromStatus / ToStatus / Comment / ActedAt |

- **初期値 = 既定フィールド名**。既定名でフィールドを作れば設定不要（置くだけ）
- 役割のフィールドが自モジュールに無ければ**デザインチェックがエラー**にする（= 契約の実装漏れ検出。ここがインターフェイス）
- 役割プロパティは自モジュールのフィールド参照としてリネームに追従する（フィールド名は後から自由に変えられる）
- UI もデータも持たない設定運搬フィールド（PermissionField と同じ流儀。DB列不要）
- 同じ契約フィールドを同一モジュールに複数置くとエラー（解決が曖昧になるため）
- フロー契約の Members / Histories は一覧フィールドであることと、一覧の先のモジュールが
  対応する契約（メンバー契約 / 履歴契約）を実装していることもチェックする
- サーバー（エンジン）は契約が無ければ明示エラーで拒否。クライアントの表示は既定名にフォールバックして保守的に動く

## 5. 権限・編集ロック（既存権限機構との連携）

**編集ロックは申請書モジュールの DataWriteCondition で宣言する**（サーバー強制＋クライアント ViewOnly が 1 宣言で両立）。

条件は**フロー行へのリンク越し参照**（検索変数 `承認.Status` / `承認.Applicant`。コアの宣言なしドットパス）で書く。
コピー列（StateDbColumn / ApplicantDbColumn）は廃止済み。dotted 宣言は不要（条件で使えば自動合成）、
未申請 = フロー行なし = null 検索で表せる。

**専用の検索コントロールは持たない**（廃止済み）。汎用の条件エディタがリンク越しパス
（`承認.Status` / `承認.Members.～` 等）を対象候補に列挙し、サンプルではフローの Status 等を
enum 付き SelectField にしてあるため値候補（承認中 等）も内部値を書かずに選べる。
状態値の enum (ApprovalFlowStatus / ApprovalMemberStatus / ApprovalStepType) は Extras の C# enum を
`[DesignEnum]` 属性（コアの新機能）で公開したもので、enum 定義ファイル不要・エンジンの文字列値と同一定義
（メンバー名 = 保存値。表示名はリソース解決）。デザイナでは通常の enum と同じ場所に出るが読み取り専用。

自動生成（§8）が親モジュールに書き込む既定条件（ユーザー変更可）:

```
OR(
  承認.Status == null,                                        // 未申請
  IN( 承認.Status, ["Returned","Withdrawn","Rejected"] )      // 編集して再申請できる状態
)
```

「承認者だけ・最終承認者だけ」のような**メンバー依存の条件**は、フローモジュールの `Members` 一覧への
**リンク越し存在条件**（コアのリンク越しList参照。`承認.Members.～`）で書く。申請書側に一覧フィールドの
複製は不要（SQL は exists、クライアントはロード済み埋め込みリストの行評価。
And で同じ一覧を指す条件は「同一行が全部満たす」に合成される = SQL と同義）:

```
// 自分が現在の承認待ち（DataWriteCondition に OR で足す）
AND( 承認.Status == "InProgress",
     承認.Members.StepType == "Approval", 承認.Members.Status == "Waiting",
     承認.Members.ApproverUser == CurrentUser.Id )

// 最終承認者の番だけ書ける（PermissionField の WriteCondition）
AND( 承認.Members.IsFinalStep == true, 承認.Members.Status == "Waiting",
     承認.Members.ApproverUser == CurrentUser.Id )
```

あわせて設定するもの:
- 申請書詳細レイアウトの DataOnlyFields に条件で使うパス（`承認.Status` / `承認.Applicant` / `承認.Members`）を登録
  （未登録でもサーバー強制は正しいが、クライアント評価が false に倒れ、承認者の番でも ViewOnly 表示になる）
- メンバーモジュールのリストレイアウト DataOnlyFields に条件が参照するフィールド（StepType / IsFinalStep）を登録
  （埋め込みリストのロード列はリンク先レイアウトで決まるため）

承認データモジュール側の既定権限（生成時に設定、デザインチェックで検証）:
- Flow / Member / History / Notification: UserWriteCondition = 不成立条件（誰も書けない）。
  読み取りは要件に応じて（承認待ち一覧・履歴表示のため UserRead は通常全員可）
- 経路マスタ 3 モジュール: UserWriteCondition = 管理者条件
- Delegation: DataWriteCondition = 自分の行のみ

## 6. 通知（NotificationModule 設定時のみ）

- 送信は `MailDispatcher` 直呼び。文面テンプレートは VariableName 表記（`{Name}` / `{承認.Status.Value}` / `{RecordUrl}`）、
  差し込みコンテキストは申請書モジュールデータ
- **Outbox パターン**: command API はトランザクション内で Notification 行を積むだけ。
  送信は Extras.Server の IHostedService（Outbox ワーカー）が非同期に実行（メール障害で承認が失敗しない・再送可能・送信ログが残る）
- v1 の通知イベント: 承認依頼（ステップ到達時、Waiting メンバー＋有効な代理人へ）/ 差し戻し・却下（申請者へ）/
  承認完了（申請者へ）/ 取り下げ（現在の Waiting メンバーへ）/ リマインド（ステップ設定に従い放置中メンバーへ。Remind 履歴を記録）
- 宛先アドレスは OrganizationBinding の MailAddressFieldName
- MultiTenant はワーカーが全テナントをループする（1リクエスト=1テナント接続の構造のため）
- メール内ワンクリック承認はトークン付き公開エンドポイント共通基盤（将来）待ち = v2。v1 は `{RecordUrl}` リンク遷移

## 7. command API

Extras.Server の Controller（ApplicationPart 自動登録・結線不要）。エンドポイントは `EndPoint` 静的プロパティで
アプリ側が変更可能（Mail の `SendMailEndPoint` と同じ流儀）。WinForms/WPF ホスト向けに `IApprovalTransportHandler`
切り替えを用意（Mail の `IMailTransportHandler` と同型）。

```
POST /api/approval/submit     … 申請書の保存データを受け、同一トランザクションで
                                親保存 → 経路解決 → フロー生成 → FK 設定 → 履歴 → Outbox
POST /api/approval/approve    … { flowId, expectedVersion, comment }
POST /api/approval/reject     … 同上（コメント必須設定に従う）
POST /api/approval/return     … ＋ { targetStepNo? }（ReturnScope 検証）
POST /api/approval/withdraw   … 申請者の取り下げ（承認が始まる前のみ）
POST /api/approval/resubmit   … 申請書の保存データを受け、親保存＋経路再解決を同一トランザクション
POST /api/approval/confirm    … 回覧の確認記録
POST /api/approval/preview    … 経路プレビュー（メンバー解決含む・書き込みなし）
```

### 全 API 共通の検証（サーバー強制）

1. アプリアクセス権＋認証ユーザーの存在（`ModuleDataIO.CheckAppAuthorization` / `GetCurrentUser`）
2. フロー状態でそのアクションが可能か（状態機械の遷移表）
3. 実行者が資格を持つか（Approve/Reject/Confirm = 現在ステップの Waiting メンバー本人、
   または有効な Delegation を持つ代理人。Withdraw/Resubmit = 申請者本人。Withdraw はさらに承認済みメンバーがいないこと）
4. expectedVersion が一致するか（フローの OptimisticLocking 列。二重承認・競合操作の防止。
   **クライアント任意の楽観ロックとは別に、command API では必須**）
5. 差し戻し先が ReturnScope の範囲か
6. コメント必須設定を満たすか
7. Submit/Resubmit 時: 経路解決の成立（承認者 0 人のステップ・条件で全ステップ消滅 → エラー）、SelfApprovalPolicy

- トランザクション: `db.StartTransaction()` → 親保存は `ModuleDataIO.SubmitAsync(Guid, List)`（public）→
  承認モジュール書き込み（システム権限の口）→ `CommitAsync()`。Outbox 行も同一トランザクション
- 承認モジュールのシステム書き込みは、テンプレートの CustomizedModuleDataIO が公開する内部追加/更新の口
  （メール履歴の `Func<ModuleData,Task>` 注入と同じ流儀）を使う
- 例外は行単位の ExceptionMessage / HTTP エラーとしてクライアントの既存エラー表示（Logger.Error）に乗せる

## 8. 自動生成と使いまわし（実装は後日・仕様のみ確定）

ユーザーが承認モジュール群を手で作るのは非現実的なため、**デザイナのコマンド（＋headless CLI）で自動生成**する。
生成の仕組み自体は汎用機能として切り出した（[関係モジュール生成機能仕様.md](関係モジュール生成機能仕様.md)。
承認フローはその最初の利用者）。

- 入口: フィールド配置時の生成提案、または Tools メニュー / CLI サブコマンド（CCFD からも同じ生成を呼べるように）
- 生成物: 選択した構成（最小/標準/フル）のモジュール定義（.mod.json）＋ テーブル作成 SQL ＋
  親モジュール側の結線（FK 列・dotted 宣言・DataOnlyFields・DataWriteCondition）＋ フィールドのマッピング設定
- **冪等**: 指定名のモジュールが既に存在すれば生成せず、フィールドのマッピングを既存モジュールに向けるだけ。
  これが「使いまわし」の実現方法 — 2 個目以降の申請書モジュールにフィールドを置いたときは参照設定のみが走る
- **共有が標準**: 全申請書モジュールが同一の Flow / Member / History（＝同一テーブル）を使う。
  承認待ち一覧・履歴・監査が全申請種別を横断できる。分けたい場合（部門ごとに承認データを分離等）は
  名前プレフィックスを指定して別セットを生成する
- 同梱サンプル画面: 承認待ち一覧（Member の ListPage: `ApproverUser = CurrentUser AND Status = Waiting`、
  「開く」で TargetModuleName / TargetId から申請書へ遷移）、履歴一覧、（フル構成時）経路管理・委任設定画面

## 9. UI（ApprovalFlowField コンポーネント）

- **ステッパー進捗表示**: StepNo グループごとにステップ名＋各メンバーの状態
  （✓承認済 / ✗却下 / ▶現在待ち / —スキップ / 代理バッジ）。現行テンプレートの 1 行文字列サマリーを構造化 UI に置き換える
- アクションボタン群（申請 / 承認 / 却下 / 差し戻し / 取り下げ / 再申請 / 確認）: 状態と資格で出し分け。
  表示制御はクライアント、強制は command API（大原則）
- コメント欄（必須設定に連動。申請・再申請時のコメントも同じ欄。差し替えたい場合はコメント欄を OFF にして
  任意フィールド＋スクリプトで `Comment` を設定するか `Approve("コメント")` 等に渡す）、
  履歴一覧（History の埋め込み表示。リッチなコメント表示が要るアプリは履歴モジュールの画面を自作する）
- **表示部品フィールドによるレイアウト分割**: `ApprovalHistoryField`（実装済）は同一モジュール上の
  ApprovalFlowField を `ApprovalFieldName` で指定し、その履歴だけを表示する（本体側は「履歴を表示」OFF）。
  状態・データは ApprovalFlowField が単一保持し、表示部品はデータも送信も持たない。
  ボタンやコメントも自由配置したい場合は ShowActions OFF ＋ ButtonField ＋ スクリプト API。
  逆にまとめた見た目を変えたい場合も、新しい Design＋Component を作ってランタイムは ApprovalFlowField を
  参照する同じ形で足す（状態の二重保持はしない）
- 申請・再申請も標準 UI が持つ（経路は OnBuildRoute スクリプトが組み立てる。アプリに残る責務は経路の組み立てだけ）
- **アクション後の挙動**: 標準 UI はその場でフィールド表示を再読込するだけ。
  親モジュールの編集可否のクライアント評価はページ読込時のデータ基準のため、その場では変わらない
  （開き直しで反映。サーバー側は DataWriteCondition が常に正）。
  その場での表示切り替えなど画面更新を作り込みたいアプリはボタンを外付けにし、
  出し分けは資格プロパティ（CanSubmit / CanApprove / CanConfirm / CanWithdraw / CanResubmitNow、
  スクリプト公開）、アクション成功後の処理はボタンの OnClick スクリプトで行う。
  モジュール再初期化の公開 API は core 側の将来課題
- 検索初期値等は通常のモジュール設計の世界（作り込み可能）

## 10. アプリテンプレートへの結線（数行・core 無改変）

1. `builder.Services.AddScoped<IApprovalContext, ApprovalContextAdapter>();`（DataService を包む小アダプタ）

## 13. 実装リスク・要検証事項

1. **システム書き込みの口の形**: メール履歴の `Func<ModuleData,Task>` 注入は追加のみだった。承認は更新も要るため
   口が 2 つになる。テンプレート側コード量とのバランスを実装時に確認
2. **Flow→Members（1 段）のシステム一括生成**: ModuleData で親子を同一トランザクション生成する経路の確認
   （ステップモジュール廃止で入れ子は 1 段に減った）
3. **ステップ状態の計算表示**: 進行済みステップと未確認回覧（非ブロック）が混在するときのステッパー表現
4. **リマインドの多重送信防止**: ワーカー多重起動（スケールアウト）時の Outbox 行ロック方式
5. **マッピングのプロパティ数**: ネスト設計オブジェクト＋デフォルト充填で運用上は見えない想定だが、
   デザイナのプロパティ UI 表示（カテゴリ折りたたみ）を実装時に確認
6. **サーバー側スクリプト実行**（v2 のルート選択・メンバー解決スクリプト向け）: スクリプトエンジンのサーバー実行可否と
   利用可能サービスの整理
