# メンバー解決機能仕様

2026-08-13 検討版（同日第2版: 予約フィールド名方式を廃止し、**明示指定（組織バインディング）＋デフォルト名**方式に変更。
CLB の既存スタイル＝デザインプロパティによる名前参照に揃え、リネーム追従・デザインチェックの既存機構に乗せる。
同日第3版: **MemberRuleField（ルール編集フィールド）**と**スクリプトからのルール組み立て**を本機能の部品として追加）。
承認フロー機能（[承認フロー機能仕様.md](承認フロー機能仕様.md)）の下層として先行設計する。
承認フローとは独立した汎用機能であり、単体で仕様を閉じる。

## 目的とスコープ

「ルール」から**実ユーザーの集合**を解決する汎用機能。

```
解決ルール（役職・上長・グループ・フィールド値…）
   ＋ 組織バインディング（アプリの組織モデルへの明示マッピング）
   ＋ 解決コンテキスト（基準ユーザー・対象モジュールデータ）
   ↓ MemberResolver.ResolveAsync
実ユーザー Id のリスト（スナップショット）
```

- **消費側（想定）**: 承認フローの承認者解決、回覧先、メール宛先、担当者割当、通知先
- CLB は組織マスタがアプリ定義（ユーザー・部署・グループはすべてユーザーのモジュール）のため、
  競合製品のように「製品組み込みの組織マスタ」を前提にできない。**組織バインディング（§2）で
  アプリの組織モデルに明示的に接続する**のが本機能の中核
- 実装の置き場所: Extras（クライアント共有=ルール型・バインディング型、サーバー=解決エンジン）。core 無改変

**非スコープ**
- 組織図の編集 UI — 組織マスタは通常のモジュール設計の世界
- サーバー側でのデザインスクリプト**実行**によるルール解決 — v2（サーバー側スクリプト実行の検証後）。
  ※スクリプトでルールを**組み立てる**こと（§6）は v1 で可能（組み立てはクライアント・解決はサーバー、の分離）。
  解決ロジック自体を差し替える逃げ道は C# 拡張（§5）

## 1. 解決の原則

1. **解決結果はスナップショット**。消費側が解決時点の実ユーザー Id を保存する。
   人事異動・組織改編で過去の解決結果は変わらない。再解決は消費側の明示操作（承認フローなら再申請・管理者操作）。
2. **確定解決はサーバーで行う**。クライアントの解決はプレビュー用途のみで、サーバーは信頼しない。
3. **解決は操作ユーザーの権限に依存しない**（申請者がユーザーモジュールの UserRead を持たなくても承認者は解決できる）。
   サーバー側はシステム権限のデータアクセスで検索する。
4. **解決結果 0 人は正常値として返す**。エラーにするかは消費側の判断（承認フローは経路解決不能としてエラーにする）。

## 2. 組織バインディング（明示指定＋デフォルト名）

アプリの組織モデルへの接続は、**消費側のデザイン（フィールドのプロパティ等）が持つバインディング設定**で明示指定する。
綴り一致の暗黙予約名は使わない（設計判断: CLB の既存スタイルは「デザインが名前で参照する」であり、
明示参照ならリネームリファクタの追従・デザインチェック・デザイナの候補表示という既存機構がそのまま効く。
暗黙予約名は衝突・リネーム破損・存在の見えにくさという弱点があるため不採用）。

```csharp
// 共有デザイン部品（消費側フィールドのプロパティにネストして持たせる）
public class OrganizationBindingDesign
{
    // ユーザーモジュールは app.clprj の Current User Module 設定をそのまま使う（ここでは指定しない）
    public string ManagerFieldName { get; set; } = "Manager";           // ユーザー→上長 Link（自モジュール参照）
    public string DepartmentFieldName { get; set; } = "Department";     // ユーザー→部署 Link
    public string PositionFieldName { get; set; } = "Position";         // 役職（Select/Text）
    public string MailAddressFieldName { get; set; } = "MailAddress";   // 通知宛先（消費側が通知を持つ場合）
    public string DepartmentManagerFieldName { get; set; } = "Manager"; // 部署→管理者 Link
    public string DepartmentParentFieldName { get; set; } = "Parent";   // 部署→親部署 Link（自モジュール参照）
    public string GroupMembershipModuleName { get; set; } = "";         // グループ所属（N:M）。空 = Group ルール不使用
    public string GroupLinkFieldName { get; set; } = "Group";
    public string GroupUserLinkFieldName { get; set; } = "User";
}
```

- すべて**デフォルト名入り**。標準構成（自動生成・テンプレート）ならユーザーは触らない。
  組織モデルが標準と違うアプリだけ、デザイナのプロパティで指定し直す
- 使うルール型が要求する項目だけ検証する（`Manager` ルールを使わなければ ManagerFieldName の存在検証はしない）
- 部署モジュールは「ユーザーモジュールの DepartmentFieldName リンクの参照先」として特定する（モジュール名の直接指定は不要）
- リネーム追従: バインディングが参照するフィールド名は、デザイナのリネームリファクタの参照収集
  （既存の CollectReference 機構）に登録する

## 3. ルール型（v1）

ルールは「型＋値＋オプション」の 1 行で表現する（デザインのコレクション項目としても、モジュールのデータ行としても持てる形。
JSON 複合ルールは v2）。

| ResolverType | ResolverValue の意味 | 解決内容 |
|---|---|---|
| `User` | ユーザー Id | そのユーザー（存在検証のみ） |
| `Group` | グループ Id または名前 | バインディングのメンバーシップモジュールを検索して所属ユーザー全員 |
| `Position` | 役職値 | ユーザーモジュールを `Position = 値` で検索。オプション `SameDepartmentOnly`（基準ユーザーと同一部署に限定、既定 false） |
| `Manager` | ホップ数（既定 1） | 基準ユーザーの上長リンクを N 回辿ったユーザー。途中で null なら**最後に辿れたユーザー**を返す（オプション `StrictHops=true` なら 0 人） |
| `DepartmentManager` | 遡り数（既定 0 = 自部署） | 基準ユーザーの部署を親リンクで N 回遡った部署の管理者 |
| `Field` | 対象モジュールデータのフィールドパス（例 `RequestedApprover.Value`、dotted 可） | フィールド値をユーザー Id として解釈。LinkField（ユーザーモジュール参照）を想定 |
| `Custom` | 拡張名 | C# 拡張（§5）に委譲 |

- 基準ユーザー: 通常は「申請者」等、消費側が渡す。`Manager` / `DepartmentManager` / `SameDepartmentOnly` が使用
- 対象モジュールデータ: `Field` が使用（承認フローなら申請書の ModuleData）
- 解決結果は重複除去した Id リスト。順序はルール記述順 → 検索順

## 4. API

### サーバー（確定解決・Extras.Server、public）

```csharp
public class MemberResolver
{
    public MemberResolver(ModuleDataAccessContext context);  // システム権限のデータアクセス＋DesignData
    public Task<MemberResolutionResult> ResolveAsync(
        IReadOnlyList<MemberRule> rules, OrganizationBinding binding, MemberResolutionContext context);
}
// MemberResolutionContext = { BaseUserId(基準ユーザー), TargetModuleData(任意) }
// MemberResolutionResult  = { UserIds, Errors(ルール単位の解決失敗。参照切れ等) }
```

- 消費側（承認フローの command API 等）がサーバー内で直接呼ぶ。Mail の「機能は MailDispatcher を直接呼ぶ」と同じ位置付け
- `ModuleDataAccessContext` はシステム権限で検索する薄いラッパ（操作ユーザーの権限フィルタを通さない）。
  実装はメール履歴書き込みと同じ「テンプレートの CustomizedModuleDataIO が公開する口」を使う

### クライアント（プレビュー・任意）

- エンドポイント `/api/member_resolution/resolve`（POST）。申請前の「この内容だと経路はこうなる」表示用
- 認証必須（[Authorize] は Mail と同様アプリテンプレート側の作法に従う）。**確定処理には使わない**

## 5. C# 拡張（v1 の逃げ道）

バインディングで表現できない組織（外部人事システム参照・特殊な兼務モデル等）向け。

```csharp
public interface IMemberResolverExtension
{
    string Name { get; }   // ResolverType=Custom の ResolverValue と一致させる
    Task<List<string>> ResolveAsync(MemberResolutionContext context, string? parameter);
}
```

- 登録はアプリテンプレート側で `MemberResolver.Extensions.Add(...)`（Mail の CreateSender と同じ「ユーザー可触コードの対応表」流儀）

## 6. MemberRuleField（ルール編集フィールド）

ルールを**モジュールのデータとして**持たせるとき（承認フローの経路マスタのメンバー行、回覧先・通知先の設定行など）の
編集 UI を提供する専用フィールド。**本機能の部品であり、承認フローには依存しない**。

- 標準フィールド（Select＋Text）でルールを編集させると「User 型なのにユーザー Id を手打ち」になり管理者 UI として
  成立しないため、**型セレクタ＋型に応じた値エディタ**の複合フィールドにする:
  - `User` → ユーザー検索ピッカー（LinkField 相当の候補検索。ユーザーモジュールは app.clprj 設定から）
  - `Group` → グループ選択（バインディングのメンバーシップ構成から）
  - `Position` → 役職値の入力/選択
  - `Manager` / `DepartmentManager` → ホップ数/遡り数の数値
  - `Field` → フィールドパス入力
  - `Custom` → 拡張名＋パラメータ
- **保存は 1 列**（型＋値＋オプションを複合値としてシリアライズ）。エンジン（MemberResolver）はこの複合値を
  そのままルールとして読める。行側は「MemberRuleField＋IsRequired(Boolean)」の 2 フィールドで済む
- 表示（ViewOnly）は人が読める形（例: `上長(1)` / `役職: 部長` / `山田太郎`）
- デザインプロパティ: OrganizationBinding（§2。候補検索・検証に使用）
- デザインチェック: 保存値の型が既知か、バインディングとの整合（§8 に委譲）

## 7. スクリプトからのルール組み立て

ルールは**スクリプトでその場で組み立てられる**（消費側が許可する場合。承認フローの「申請時にスクリプトで経路を組む」等）。

```csharp
// スクリプトオブジェクト MemberRule（ファクトリ。ExtrasDesignerInitializer で登録）
var a = MemberRule.User(選択ユーザー.Value);      // 名指し（その場指定）
var b = MemberRule.Manager(1);                    // 申請者の上長
var c = MemberRule.Position("部長");
var d = MemberRule.Group("経理");
var e = MemberRule.Field("RequestedApprover.Value");
var f = MemberRule.Custom("HrSystem", "dept=A1");
```

- **組み立てはクライアント・解決はサーバー**の分離を守る。スクリプトが作るのはルール（宣言）であり、
  実ユーザーへの解決は常にサーバーの `MemberResolver` が行う（§1 の原則 2・3 は崩れない）
- 消費側（承認フロー等）はスクリプト由来ルールの受け入れ可否を自分のデザインフラグで制御する
  （信頼モデルの判断は消費側の責務。本機能は組み立て手段を提供するだけ）

## 8. デザインチェック

消費側のバインディング＋ルールに対して（使用ルール型が要求する項目のみ）:

- [ ] ResolverType が既知値か
- [ ] `Manager` / `DepartmentManager` 使用時、バインディングが指すフィールドが存在し型が正しいか
      （上長 = ユーザーモジュール自モジュール参照 LinkField、部署 = LinkField、部署側の管理者/親リンク）
- [ ] `Position` 使用時、役職フィールドの存在
- [ ] `Group` 使用時、メンバーシップモジュールと 2 つのリンクフィールドの存在
- [ ] `Field` 使用時、対象モジュールに該当フィールドパスが存在するか
- [ ] バインディングのフィールド名が空でないか（使用ルールが要求する場合）

チェックの実装は消費側フィールド型に持たせ、判定ロジックは本機能が提供する（ドメイン判断はフィールド型・チェックは問い合わせるだけ、の既存方針）。

## 9. 確認項目（主要テスト観点）

- [ ] 各 ResolverType の解決結果（正常系・0人・参照切れ）
- [ ] `Manager` のホップ途中 null（既定=最後に辿れた人 / Strict=0人）
- [ ] `DepartmentManager` の遡り（自部署→親→ルート到達で打ち切り）
- [ ] `SameDepartmentOnly` の絞り込み
- [ ] 重複除去（複数ルールが同一ユーザーに解決）
- [ ] バインディングの既定名を変更した構成で全ルールが動く（明示指定の検証）
- [ ] MemberRuleField: 各型のエディタ⇄保存値のラウンドトリップ、ViewOnly 表示、未知型の保存値をデザインチェックが検出
- [ ] スクリプト組み立てルールとデータ保存ルール（MemberRuleField）が同一の解決結果になる
- [ ] 操作ユーザーがユーザーモジュールを UserRead できなくても解決できる（システム権限）
- [ ] 論理削除ユーザー（`LogicalDelete`）は解決から除外される
- [ ] プレビュー API とサーバー確定解決が同一結果
- [ ] 組織変更後、保存済みスナップショットが変わらないこと（消費側テストと重複可）
