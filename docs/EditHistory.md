# 編集履歴

モジュールに **EditHistoryField** を 1 つ置くと、そのモジュールのレコードの保存 (作成・更新・削除) ごとに
レコード全体 (明細を含む) のスナップショットが履歴モジュールへ記録されます。
詳細画面には版の一覧が出て、変更されたフィールドの「旧 → 新」、その版のレコード全体の表示、
その版の内容へのフォームの巻き戻しができます。履歴は通常のモジュールに保存されるため、
一覧・検索・権限はいつものローコードのやり方でできます。

- [概略](#概略) — 何ができるか、導入の流れ
- [詳細](#詳細) — 記録、表示、復元、復活、従属レコード、権限、契約、設計チェック、運用、セットアップ、サーバーの結線

---

## 概略

### できること

- **保存ごとにレコード全体を記録**。従属レコード (明細やガントチャートのタスクなど) も一緒に 1 版になる (明細だけの変更も親の 1 版)
- **削除も記録** (削除前の内容)。履歴モジュールの一覧を ChangeType = Delete で絞れば「削除済みレコード一覧」
- **版の一覧** — 版番号・変更種別・変更者・日時と、変更されたフィールドだけの「旧 → 新」。明細は行の追加 / 削除 / 変更
- **この版を表示** — その版のレコード全体を表示専用のダイアログで表示。変更されたフィールドを強調 (明細の行・ガントチャートのタスク・カレンダーの予定・カード・マーカーも 追加 / 変更 / 削除 で強調)
- **この版に置き換える** — 「この版を表示」のダイアログから、見ている版の内容を編集中のレコードに入れる。**保存はユーザーが行う** (保存前に確認・一部だけ直す、ができる)。保存すると新しい版として記録される (履歴は巻き戻らない)
- **削除したレコードの復活** — 履歴モジュールの詳細に EditHistoryUndeleteButtonField を置く。論理削除のモジュールなら Id を保ったまま明細ごと戻る (リンクは切れない)。物理削除なら作り直す
- **履歴から対象レコードへ** — 履歴モジュールに本体の AnchorTagField を置き、ModuleVariable に `ModuleName.Value`、IdVariable に `DataId.Value` を指定すると、その履歴行のレコードを開くリンクになる
- CSV / Excel の一括取込や API からの保存も記録される (保存経路が同じ)
- 版の内容は読む人の権限に合わせて返される (読めない項目・行は履歴経由でも見えない)

### フィールド

| フィールド | 置く場所 | 役目 |
|---|---|---|
| EditHistoryField | 履歴を取るモジュールの詳細レイアウト | 「履歴を取る」の宣言と、版の一覧・この版を表示・この版に置き換える |
| EditHistoryContractField | 履歴モジュール | 役割 → フィールド名の対応表 (UI なし) |
| EditHistoryUndeleteButtonField | 履歴モジュールの詳細レイアウト | 削除したレコードの復活ボタン |

### 導入の流れ

1. **履歴モジュール**を作る (全モジュールで 1 つ共有してよい)。デザイナの **Tools > 編集履歴のセットアップ** (または CLI の `edit-history-setup`) が、
   契約・復活ボタン・対象レコードリンク・検索レイアウト・対象モジュール enum・ページリンク込みの履歴モジュールとテーブル作成 DDL を生成する。
   手で作るならフィールドは ModuleName / DataId / ChangeType / Snapshot (必須) と UserId / DateTime (任意)。
   **EditHistoryContractField** を 1 つ置く (既定名でフィールドを作れば設定不要)。モジュールの CanCreate / CanUpdate は false にする。テーブル定義例:

   ```sql
   CREATE TABLE edit_histories (
     id          BIGSERIAL PRIMARY KEY,
     module_name TEXT NOT NULL,
     data_id     TEXT NOT NULL,
     change_type TEXT NOT NULL,
     snapshot    TEXT NOT NULL,
     user_id     TEXT,
     date_time   TIMESTAMP
   );
   CREATE INDEX ix_edit_histories_target ON edit_histories (module_name, data_id);
   ```

2. 履歴を取りたいモジュールに **EditHistoryField** を置き、`HistoryModuleName` に履歴モジュールを設定。詳細レイアウトの右カラムかタブに配置
3. サーバー側は `Codeer.LowCode.Blazor.Extras.Server` の **EditHistoryRecorder** を `CustomizedModuleDataIO` に 1 行で登録 (アプリテンプレートは登録済み。[サーバーの結線](#サーバーの結線))

## 詳細

### 記録

- サーバーの `EditHistoryRecorder` (本体の IO インターセプタ) が保存を包む。トランザクションのルートレコード 1 件につき履歴 1 行
- 作成・更新は本体の保存が成功した後に保存後のレコードを、削除は本体の保存の前に削除前のレコードを読んで記録する
- 読む範囲は「レコード本体 ＋ 従属レコードの宣言 (`IOwnedRecordsFieldDesign`) の先」。子・孫も再帰。何が従属かは各フィールドが決める

  | フィールド | 従属として版に入るもの |
  |---|---|
  | 一覧 (ListField 等) | 親の画面で行を追加・更新・削除できる一覧と、親と一緒に消える一覧 (DeleteTogether)。参照するだけの一覧 (編集できない一覧) は入らない |
  | 埋め込みモジュール (ModuleField) | 参照している子レコード (DbColumn に子の Id を持つ埋め込み。DbColumn か ModuleName が無い埋め込みは対象外)。子の明細・子の中の埋め込みも再帰 |
  | Gantt / Calendar / TaskBoard / MarkerList | 自分の子レコード。Gantt は依存関係も (`フィールド名:Dependencies`。DependenciesModule があるときだけ) |

- 従属レコードを行のモジュール側 (子自身のページ) で個別に保存した変更は、親の版にはならない
- 読み直しは本体の内部読み = 操作ユーザーの権限に関係なくレコード全体 (全列・全従属レコード) を記録する。履歴は「レコードがどう変わったか」の記録なので、書いた人の権限で欠けない。読む人の権限は返すときに落とす ([権限](#権限))
- DB で NULL だった列は null の値として入る (その版で空だったことが残り、復元で空に戻る)
- 読み出せない列 (書き込み専用の列 = パスワードのハッシュなど) は版に入らない。PasswordField も DB 列を持たないので入らない
- 従属レコードの循環は「同じレコードを二度読まない」で止める (モジュール単位ではない)。自己参照の従属 (カテゴリ→子カテゴリが同じモジュール、部品表など) も、深さのまま親の一部になる (差分・版表示・復元も同じ)
- 変更種別は `EditHistoryChangeType` (Add / Update / Delete / Restore) のメンバー名。Restore は削除したレコードの復活 (論理削除の取り消しも物理削除からの作り直しも)。デザイン enum として公開されるので、履歴モジュールの ChangeType を SelectField (EnumName = `EditHistoryChangeType`) にすれば表示名付きで一覧・検索できる
- Id を変えた更新 (手入力 Id の書き換え・複合 Id の構成項目の変更) は、旧 Id の版を新しい Id に付け替えてから記録する (履歴が繋がる)
- 一括取込も記録される。履歴対象モジュールの投入は本体の一括 INSERT 経路 (`BulkAddThreshold` 以上の純追加) を使わず 1 行ずつ入る (採番 Id を履歴に使うため)
- 添付ファイルはファイル名とキーだけ記録し、実体は履歴に残さない。ただし履歴を持つモジュールのレコードに触る保存では、削除・差し替えで外れる添付を本体の一時領域 (期限後に消える) へ送らず、そのまま残す。削除したレコードを復活させると同じ添付を参照し、実体も残っているので開ける。DB 列格納 (DbColumnFileContent) の添付は行と一緒に消えるので戻らない。残した添付は履歴の版を消しても消えない (履歴と同じく手で整理する)
- **ExecuteSqlField** も記録される (SQL は同じ保存の中で走る)。Update / Delete タイミングは通常どおり保存後・削除前の内容。Create タイミングは `NewId` で採番 Id が返る設定のときだけ記録される。Standalone (Add / Update / Delete の無い送信で SQL だけ実行) は送信前後のレコードを比べ、レコード自体が変わったときだけ 1 版にする (他のテーブルだけを変える SQL は履歴にならない)
- **承認フロー (ApprovalFlowField) との組み合わせ**: 申請・再申請は申請書の保存を通るので申請者の版になる (作成 / 更新)。承認・却下・差し戻し・取り下げ・確認は承認モジュールだけを書く (申請書の保存を通らない) ので版にならない = 誰がいつ承認したかは承認履歴 (ApprovalHistory) が持つ。承認フローの FK はサーバーが保存の後に書くので、版の差分には出さず「この版に置き換える」でも触らない
- **自動保存 (AutoSubmitField) との組み合わせ**: 自動保存も通常の保存と同じ経路なので保存ごとに版になる (遅延の間にまとめて保存された変更は 1 版)。履歴の版一覧は自動保存のたびに読み直される。「この版に置き換える」で反映した内容も自動保存されて次の版になる (ユーザーの保存操作は要らない)

#### 版にならない保存

- 「変更なしで保存」は送信自体が起きないので版は増えない。何も保存しない送信 (承認の申請で申請書に変更が無いときなど) も版にならない
- 親の版に含めない従属レコード (除外・行ごとに記録) の行だけを変えた保存は、親の版にならない
- 保存後のレコードを特定できない・読めないときは、保存は成功のまま版を作らない: ExecuteSqlField の Create タイミングで `NewId` が無く採番 Id が返らないとき、保存後のレコードが読めないとき (保存の中でレコードが消えた等)。理由は `EditHistoryRecorder` に渡したログに出る ([サーバーの結線](#サーバーの結線))

#### 記録の失敗

- 履歴の書き込みに失敗すると保存も失敗 (ロールバック) になる。履歴が静かに欠けるより、保存できないことがユーザーに見える方がよいため
- EditHistoryField があるのに履歴モジュール・契約が無い設計 (デザインチェックが指摘する不備) も保存が失敗する

### 表示

- 画面を開いたときは件数だけ (「履歴 n 件」) を読み、「表示」を押してから版を読む (版はスナップショット込みで重いので、開くたびには読まない)。展開したまま保存すると版を読み直し、展開していなければ件数だけ読み直す。「閉じる」で件数の表示に戻る
- `PageSize` (既定 20) ずつ読み、「さらに表示」で次を読む
- 未保存のレコードでは読まない。詳細レイアウト専用で、一覧の行では読まない
- 版番号は保存せず、閲覧時に件数から採番する (古い方から 1, 2, ...)。「閲覧者に見える版の中での連番」なので、履歴モジュールに閲覧条件があると人によって番号が変わる。1 回の読み込みの中では固定 (「さらに表示」の間に版が増えてもずれない)。並びは DateTime 役割があれば日時、同着と DateTime 役割なしは Id の降順
- 各版は折りたたみで、閉じた状態は版番号・変更種別・変更者・日時と要約 (作成 / 削除 / 復活 / 変更 n 項目: 名前, ...)。開くと前の版との差分と「この版を表示」
- 差分は変わった項目だけ。値フィールドは「表示名: 旧 → 新」(候補・リンクは表示名、日付・数値はフィールドの書式、UTC 保存の日時はローカル時刻)。従属レコードは行 Id で突き合わせて「追加 n 件 / 削除 n 件 / 変更 n 件」と行ごとの内訳 (行は行番号で示す。追加行は値、削除行は打ち消し、変更行は変わった項目)
- 作成・削除・復活の版は差分を出さない (「レコードが作成されました」等。内容は「この版を表示」)
- 履歴を取り始める前からあったレコードの最初の版、前の版の内容がその人に見えない版は、「前の版なし」として差分を出さない
- 「旧 → 新」の文字列を出すのは文字列・数値・真偽・日付時刻・候補・リンク・ファイル (名前) のフィールドだけ。それ以外の型 (独自のデータクラスを持つフィールド) は変わったかどうかだけを「変更あり」として名前で出し、内容は「この版を表示」(本物のコンポーネントで描く) で見る。一覧は要約、全体は版表示、の二層構造
- 「この版を表示」は自モジュールの詳細レイアウト (`LayoutName`、空なら既定) をそのまま使って表示専用のダイアログに出し、変更フィールドを緑の枠で強調する。保存ボタンと履歴フィールド自身は出さない。従属レコードは DB を読まずに版の行をそのまま表示する: 追加 = 行全体 / 変更 = 行に枠 + 変わったセル / 削除 = 前の版の行を元の位置に差し込んで打ち消し (Gantt のバーは枠線)。差分のある項目が表示範囲に無ければ Gantt / Calendar はその項目の日 (月) へ移動する
- 埋め込みモジュール (`ModuleField`) は明細と同じ見え方: 差分は「埋め込みのフィールド名 → 行 1 の項目ごとの 旧 → 新」(参照が付いた版は追加行、外れた版は削除行)。版表示では版の子レコードをそのまま見せ、変わった項目が強調される

### 復元 (この版に置き換える)

- 「この版を表示」のダイアログのボタン「編集中の内容をこの版に置き換える」(以下「この版に置き換える」) で行う。表示専用でないレコードの、最新でない版に出る (最新の版と削除の版には出ない)。確認は出ない (内容を見てから押す)
- EditHistoryField の `CanRestore` (既定 true) を false にすると、「この版に置き換える」も削除したレコードの復活もできなくなる (履歴は見るだけ。版の一覧・差分・「この版を表示」はそのまま)。復活はサーバーも拒否する
- 値フィールドは変更扱いで反映 (OnDataChanged スクリプトも動く。従属レコードの今ある行の中の項目も同じ)。足した行の内容は、一覧にまとめて行を足すときと同じく連動なしで入る (変更扱いにはなる)。ユーザーが保存して確定する = 権限・検証・楽観ロックは通常の保存と同じ。その保存も 1 版として記録される
- 従属レコードは行 Id で突き合わせ、既存行は更新、余った行は削除、無い行は追加する。孫の明細も同様。余った行の削除では、一覧の「削除前に確認」のメッセージは出ない
  - 無い行の明細モジュールが**論理削除**なら、Id を保ったまま復活する (保存に「その版からの削除の取り消し」が同梱され、サーバーが同じトランザクションで戻す)
  - **物理削除**なら新しい行として追加する (Id は振り直し)
  - Gantt の依存関係も版の行で差し替える。新しい行として作り直したタスクを指す依存関係は新しい行に付け替え、版にも今にも無いタスクを指す依存関係は落とす
- サーバーが取り消す (Id を保って復活させる) 行は「版にあり・今は削除中・その人に差分として見えている」行だけ。削除されていない行と、その人に見えない行は触らない。戻せない行 (削除権限が無い等) が 1 つでもあれば保存全体が失敗する (部分反映はしない)
- 埋め込みモジュール (`ModuleField`): 版の子と今の子が別レコードなら (親の参照が変わっていた) 版の子に差し替えてから、子の項目ごとに反映する (子の明細も行 Id で突き合わせ)。親の保存に子の更新が乗り、同じトランザクションで戻る。版に子が無ければ触らない (参照を外す操作は無い)
- 対象外: システムフィールド (Id / 楽観ロック / 作成・更新・削除の記録 / 論理削除)、リンク越しの派生値、従属でない一覧、添付ファイル、書き込み権限のないフィールド、承認フローの FK。反映できる項目が 1 つも無かったときはその旨のメッセージが出る (フォームは変わらない)
- 従属レコードの差し替えはフィールドが持っている行に対して行う。全件を持たないフィールド (サーバーページングの一覧) は版の全件と比べられないので**設計チェックで指摘** (`EditHistoryFieldDesign:4`。子・孫・埋め込みの中も)。一覧はメモリ内ページングか件数制限なしにする。Gantt / Calendar / TaskBoard / MarkerList は差し替え前に全件を読み直すので対象外
- ExecuteSqlField を使うモジュールでは、戻るのはレコード (と従属レコード) の内容だけ。SQL が他のテーブルや他のレコードに書いたものは履歴に無いので戻らない (履歴は「このレコードがどう変わったか」の記録として使う)

### 削除したレコードの復活

履歴モジュールの詳細に置いた EditHistoryUndeleteButtonField で行う。クライアントは削除の版の履歴行の Id だけを送り、サーバーがその版のスナップショットからレコード全体を 1 トランザクションで戻す (ChangeType = Restore の版が記録される)。復活後はそのレコードの詳細に遷移する。

- 復活できるのは次をすべて満たすときだけ (ボタンが出ない・送ってもサーバーが拒否する)
  - その版がそのレコードの最新の版で、削除の版である (復活済み・変更済みのレコードの古い削除の版からは復活できない)
  - 対象モジュールの EditHistoryField の `CanRestore` が true (既定)
  - 今そのレコードが無い (削除中)。版の削除で Delete の版が最新に戻った場合や、履歴を通らない経路で戻っていた場合に、同じレコードをもう 1 件作らない
- **論理削除**: Id を保って取り消す。親と一緒に消えた従属レコード (子・孫) も戻す。親の削除が子を消すときと同じく、子の行はユーザーの権限や行の条件を見ない (子モジュールの CanDelete だけ)。物理削除モジュールの子は作り直す
- **物理削除**: 作り直す。手入力 Id (または複合 Id) のモジュールは元の Id。自動採番は新しい Id で、子は親の新しい Id で作り直す
- 作り直して Id が変わった行を指していた項目 (Gantt の依存関係が持つ先行・後続のタスクの Id など、従属レコードの宣言の `References`) は、作り直した行の Id に付け替える
- 新しい Id になったとき (自動採番の物理削除) は、旧 Id の版を新しい Id に付け替える = 復活したレコードを開けば最初からの履歴が見える。作り直した子 (自分の履歴を持つ行モジュール) も同じ。履歴の行を書き換えるのは、これと Id を変えた更新だけ
- 物理削除からの作り直しでは Id が変わるので、そのレコードを Id で参照していた他のレコードのリンクは繋がらない。リンクを保ちたいモジュールは論理削除にするか、コードで参照する (LinkField の ValueVariable)
- 埋め込みモジュール (ModuleField) の子は親の削除では消えないので、復活では親の参照を版の子に戻すだけ (子が消えていれば版の内容で作り直して参照する)
- 除外した従属レコードは版に無いので戻らない。行ごとに記録する従属レコードは、各行の履歴 (行の削除の版) から個別に復活する
- 版に無い列 (書き込み専用の列) は作り直しでは戻らない (ログインアカウントを作り直したときはパスワードを設定し直す)
- 権限は削除と同じ = 対象モジュールの CanDelete と UserRead / UserWrite 条件に加えて、行の条件 (DataRead / DataWrite) を削除前の内容に当てる。ボタンは削除できる人にだけ出る
- **退避 (削除テーブルへの移動) とは併用できない** (デザインチェック `EditHistoryFieldDesign:3`)。履歴を入れるモジュールの削除は論理削除か物理削除にする。Id を保った復活が要るなら論理削除

### 従属レコードの扱い (含める / 除外 / 行ごとに記録)

従属レコードは既定で親の版に入るが、EditHistoryField で従属ごとに扱いを変えられる。指定は従属宣言の名前 (通常はフィールド名) で、子・孫・埋め込みの中は `Items.Details` のようにドット区切り。

| 扱い | 指定 | 記録 | 差分・版表示・復元 |
|---|---|---|---|
| 含める | 既定 | 親の版に入る | 親の画面で行う |
| 除外 | `ExcludedOwnedRecords` | 履歴に含めない (読みもしない。件数の多い一覧向け) | すべて対象外 (版表示でもその一覧は出さない) |
| 行ごとに記録 | `IndividuallyRecordedOwnedRecords` | 親の版には入れず、親の保存に乗った行 (作成・更新・削除) を行のモジュール自身の履歴に 1 行 1 版で記録 | 行のモジュールの画面で行う |

- 行ごとに記録する先のモジュールには EditHistoryField が要る (その履歴モジュールに書く)。親の画面から保存しても、行のモジュールで保存したのと同じ版になる (作成は採番 Id、削除は削除前の内容)。親を削除したときは、一緒に消える行の削除の版もサーバーが作る
- 除外・行ごとの行だけを変えた保存は親の版にならない
- 除外・行ごとを指定する前に記録された版にその従属レコードが入っていても、読む側で外す
- **含める先のモジュールが自分の EditHistoryField を持つ**とき、このモジュール経由の編集はこのモジュールの版にだけ記録され、そのモジュールの履歴に穴が空くので設計チェックが指摘する (`EditHistoryFieldDesign:11`)。除外か行ごとに指定すると指摘は消える
- 親に EditHistoryField が無い (親には版が無い) ときは、自分の EditHistoryField を持つ従属レコードの行は自動で行ごとに記録される (親の削除で一緒に消える行の削除の版も作る)
- 同じ子モジュールに「含める」経路と「行ごと」の経路の両方があるとき (2 つの一覧で同じモジュールを持つ等) は、行ごとの指定が 1 つでもあればそのモジュールの行は行ごとに記録する。どの経路から来たかは判定しないので、設計側で揃える
- 全件性のチェック (`:4`) は含めるものだけが対象なので、除外・行ごとの一覧はサーバーページングのままでよい
- パスと `LayoutName` はフィールド・レイアウトのリネームに追従する

### 権限

- 履歴の読み取りは通常のモジュールデータ API = **履歴モジュールの UserRead / DataRead 条件がそのまま効く**。履歴を見せたくないユーザーには履歴モジュールを読めなくすればよい (EditHistoryField は「履歴はありません」になる)
- 版の内容 (Snapshot) は返すときに読む人の権限に落とす。規則は通常の読み出しと同じ

  | 読む人の権限 | 返る内容 |
  |---|---|
  | 対象モジュールを読めない (UserRead) | 空 (版は見えるが内容・差分・復元は無い) |
  | 行の閲覧条件 (DataRead) に合わない版 | 空 |
  | 読めない項目 (PermissionField) | その項目を外す |
  | 読めない子モジュールの従属レコード・閲覧条件に合わない行 | その行を外す (埋め込みモジュールは参照だけ残す) |
  | 行のモジュールが今の設計に無い (モジュールを改名・削除する前の版) | その行を外す (対象モジュール自体が無ければ空) |

- 行の閲覧条件は「レコード自身の列は版の内容、リンク越しの値は今のリンク先」で判定する (通常の読み出しが今のリンク先を結合するのと同じ)
- 行の閲覧条件を版の内容で判定できないとき (条件が版に無い一覧の行を使う 1:N = 参照するだけの一覧・除外した一覧・リンク越しの一覧) は読めない扱いになる。その条件で履歴の内容を見せたいなら、条件を版の内容で判定できる形 (自モジュールの列・従属として含める一覧・リンク先の列) にする
- 一覧・詳細・Excel / CSV ダウンロードなど本体が返すレコードは全部この後処理を通るので、履歴モジュールを直接読んでも生の値は見えない
- Snapshot は検索条件・並びに使えない (使った読み出しはサーバーが拒否する)。検索・並びは DB の生の内容に対して走るので、返る行の有無から読めない値を推測できてしまうため。履歴の検索は ModuleName / DataId / ChangeType / UserId / DateTime で行う
- 差分表示と復元は、その人に返された内容だけを扱う (読めない項目は差分に出ず、復元でも触らない)。明細行の項目は行のモジュールの権限で判定する
- 履歴モジュールの版は**システムだけが書く**。履歴モジュールの CanCreate / CanUpdate は false にする (デザインチェック `EditHistoryContractFieldDesign:3`)。画面や API から版を足す・書き換える送信はサーバーが拒否する (別のモジュールの送信に混ぜた行も同じ。復活は版の内容を信用して行うため)。古い版の削除 (CanDelete と UserWrite) はできる。履歴の書き込み自体は内部経路で、操作ユーザーの書き込み権限に依存しない
- 「この版に置き換える」は対象モジュールの編集権限 (表示専用なら出ない)。復活は削除と同じ権限

### 契約フィールド (フィールド名の対応表)

履歴モジュールに `EditHistoryContractField` を置き、役割 → 自モジュールのフィールド名を宣言する。既定名で作れば設定不要。

| 役割 | 型 | 内容 | 必須 |
|---|---|---|---|
| ModuleName | Text / Select | 対象モジュール名。Select + enum (メンバー名 = モジュール名 / 表示 = 画面上の名前) で一覧の表示と検索を読み替えられる。enum は任意 (無い・空なら素のモジュール名) | ○ |
| DataId | Text | 対象レコードの Id | ○ |
| ChangeType | Text / Select | Add / Update / Delete / Restore | ○ |
| Snapshot | Text | レコード全体の JSON | ○ |
| UserId | Link (ユーザー) / Text | 保存したユーザー | - |
| DateTime | DateTime | 保存日時。フィールドの SaveAsUtc に従う (本体の CreatedAt と同じ) | - |

履歴モジュールには他のフィールドを足してもよい (記録側は役割しか書かない)。役割のフィールド名はリネームに追従する。

### 設計チェック

| コード | 内容 |
|---|---|
| `EditHistoryFieldDesign:1` | 履歴モジュールに EditHistoryContractField が無い |
| `EditHistoryFieldDesign:2` | 同じモジュールに EditHistoryField が複数ある |
| `EditHistoryFieldDesign:3` | 退避 (DeleteArchiveField) と併用している |
| `EditHistoryFieldDesign:4` | 親の版に含める従属レコードが全件を持たない (サーバーページングの一覧) |
| `EditHistoryFieldDesign:5` | 除外・行ごとのパスが従属宣言に無い |
| `EditHistoryFieldDesign:6` | 行ごとに記録する先のモジュールに EditHistoryField が無い |
| `EditHistoryFieldDesign:7` | 同じパスを除外と行ごとの両方に書いている |
| `EditHistoryFieldDesign:8` | 履歴モジュール自身に置いている |
| `EditHistoryFieldDesign:9` | Query モジュールに置いている |
| `EditHistoryFieldDesign:10` | 一覧レイアウトに置いている |
| `EditHistoryFieldDesign:11` | 親の版に含める先のモジュールが自分の EditHistoryField を持つ |
| `EditHistoryContractFieldDesign:1` | 役割のフィールドの型が違う |
| `EditHistoryContractFieldDesign:2` | ModuleName の enum にメンバーがあるのに、記録元モジュールのメンバーが無い |
| `EditHistoryContractFieldDesign:3` | 履歴モジュールの CanCreate / CanUpdate が true |
| `EditHistoryUndeleteButtonFieldDesign:1` | 契約フィールドの無いモジュールに置いている |

役割のフィールドが無い・必須の役割が空・契約フィールドの重複もエラーになる。

### スクリプト

| フィールド | メンバー |
|---|---|
| EditHistoryField | `Expand()` / `Collapse()` / `Reload()` / `LoadMore()`、`IsExpanded` / `IsLoaded` / `IsBusy` / `TotalCount` / `HasMore` |
| EditHistoryUndeleteButtonField | `Undelete()` (確認のうえ復活し、できたら true)、`IsBusy` / `ButtonText` |

### 運用

- 履歴モジュールは通常のモジュールなので、古い版の削除は履歴モジュールの一覧から行える。セットアップの既定は削除できない設定 (CanDelete が false・誰も書けない) なので、消す運用にするなら CanDelete を true にして、消す人に UserWrite を開ける。保持期間の自動削除は持たない
- 版を消すと、残った版の版番号は詰まる (版番号は閲覧時の連番)
- フィールドを足した・消した・改名した・型を変えた後の古い版は、今の設計で読む。今の設計に無い項目は差分・版表示・復元で無視される (フィールドの改名は追従しない = 別の項目)。型を変えた項目の古い値は書式に合わなければそのまま出す
- モジュールの改名にも追従しない。版は記録したときのモジュール名で残るので、改名前の版は改名後のモジュールの履歴には出ない。従属レコードのモジュールを改名・削除したときは、それより前の版の中のその行は返されない (読めるかどうかを今の設計で判定できないため)
- EditHistoryField を外しても、記録済みの履歴は履歴モジュールに残る
- 編集履歴は利用者向けの変更履歴で、監査ログではない (失敗した操作・閲覧・ログインなどは記録しない)

### セットアップ (履歴モジュールの生成)

デザイナの **Tools > 編集履歴のセットアップ**。履歴モジュール名 (既定 EditHistory)・データソース・変更者リンクのユーザーモジュールと表示名フィールド・
対象モジュール enum を作るか・ページリンクを追加するか、を聞いて次を生成する (冪等。既にあるものは触らない):

- 履歴モジュール (契約 EditHistoryContractField・復活ボタン・対象レコードリンク・一覧 / 詳細 / 検索レイアウト・作成 / 更新 / 削除できない設定と「誰も書けない」保護条件)
- 対象モジュール enum `EditHistoryTargetModule` (空)。メンバー (名前 = 対象モジュール名 / 表示 = 画面上の名前) は対象モジュールごとにユーザーが足す。
  作らない場合は ModuleName を素の名前で運用する
- PageFrame のページリンク「編集履歴」(新規作成なし・詳細遷移あり・Id の降順)
- テーブル作成 DDL (結果ダイアログでその場で実行できる)。対象レコードの検索用に (module_name, data_id) のインデックスを含む (SQL Server / Oracle はインデックスを張れる長さの列に直してから張る)

対象モジュール側 (EditHistoryField の配置) とサーバーの結線は生成しない (結果ダイアログに手順が出る)。

```
<designer.exe> edit-history-setup "<projectDir>" [--history-name EditHistory] [--data-source <name>] [--user-module AppUser] [--user-name-field <表示名フィールド>] [--no-enum] [--no-pageframe] [--ddl-out "<path.sql>"]
```

### サーバーの結線

`EditHistoryRecorder` (`Codeer.LowCode.Blazor.Extras.Server`) は本体の IO インターセプタ (`IModuleDataIOInterceptor`、Codeer.LowCode.Blazor 1.3.37)。1 つ登録すると保存 (記録・復活) と読み出し (Snapshot を読む人の権限に落とす) の両方に効くので、片方だけ結線した状態にならない。アプリテンプレートの `CustomizedModuleDataIO` に入っている形:

```csharp
public CustomizedModuleDataIO(DesignData designData, IAuthenticationContext authenticationContext, IDbAccessor dbAccess, ITemporaryFileManager temporaryFileManager)
    : base(designData, authenticationContext, dbAccess, temporaryFileManager)
{
    //編集履歴 (結線はこの 1 行)
    AddInterceptor(new EditHistoryRecorder(designData));
}
```

- `EditHistoryRecorder(designData, logError)` の `logError` (`Action<string>`) に `ILogger` の Warning 等を渡すと、版を作らなかった理由・履歴モジュールへの書き込みの拒否・復活の失敗理由・読めなかったスナップショットがログに出る。渡さなければどこにも出ない (アプリテンプレートは渡していない)
- 履歴の書き込みと記録の元の読み直しは、インターセプタに渡る本体の内部操作で行うので、ホスト側に追加のメソッドは要らない
- 記録は保存と同じトランザクションの中で行う (`SubmitWithTransactionAsync` 経由の保存)

### 独自の拡張フィールドを履歴に参加させる

別モジュールのレコードを自分で読み書きする独自フィールドは、本体 (Codeer.LowCode.Blazor 1.3.37) のインターフェースを実装すると、子レコードが親の版に入る。Extras を参照する必要はない。

**デザイン: `IOwnedRecordsFieldDesign.GetOwnedRecords(IModuleDesigns modules)`** — 子レコードが版に記録され、差分に出る。引数は全モジュールのデザイン (core 1.3.45 から)。結び付きが相手のモジュールの設計で決まるフィールドはこれを見て条件を組み立てる。自分の設定だけで決まるフィールドは使わなくてよい。

| 宣言 (`OwnedRecordsDesign`) の項目 | 内容 |
|---|---|
| `Name` | 宣言の名前。通常はフィールド名。2 つ目以降は `フィールド名:接尾辞` |
| `Condition` | 子レコードの検索条件 (親への束縛を含む) |
| `HoldsAllRecords` | ランタイムが全件を持てるか。持てないなら false (設計チェック `:4` の対象になる) |
| `IsReferencedByOwner` | 親が行を参照する宣言なら true (埋め込みモジュール)。行が無いときは参照を戻すだけで、行の作り直しも削除もしない。既定は false (行が親を参照する = 明細) |
| `References` | 行の項目のうち、同じモジュールの他の宣言の行を Id で指すもの (項目名 → 指す先の宣言の名前)。行を作り直して Id が変わったら、指す先が付け替わる |

**ランタイム: `IOwnedRecordsField`** — 「この版に置き換える」で子レコードが戻り、「この版を表示」で版の子レコードが表示される。
実装するのは行の出し入れと表示だけで、行の突き合わせ・内容の反映・消えた行の扱い・孫への再帰・指す先の付け替えは本体が行う。

| メンバー | 実装する内容 |
|---|---|
| `AllowLoad` | false のとき DB から読まない |
| `LoadOwnedRecordsAsync(name)` | 全部の行を返す (表示範囲しか読んでいなければ全件を読み直す) |
| `AddOwnedRecordAsync(name, id)` | 行を 1 つ足して返す。id が null なら新しい行、あればその Id の既にある行 (内容は入れない) |
| `RemoveOwnedRecordAsync(name, record)` | 行を外す (確認のメッセージは出さない) |
| `RefreshOwnedRecordsAsync(name)` | 行から作っている表示を作り直し、変更を通知する |
| `ShowOwnedRecordsAsync(name, rows)` | DB を読まずに、渡された行を表示専用で見せる。行のモジュールは `OwnedRecordRow.CreateModuleAsync` で作る |

版表示の強調は、行のモジュールを描くフィールド (一覧など) なら `OwnedRecordRow.CreateModuleAsync` が行とセルに付ける。
行のモジュールを描かない項目 (バーやカードなど) には `OwnedRecordRow.ClassName` を出す (行のモジュールの `ClassName` はレイアウトのデザインで付けたクラスを含むので、項目には出さない)。

サーバーが保存とは別のタイミングで書く値を持つフィールド (承認フローの FK のようなもの) は、デザインに `IEditHistoryExcludedFieldDesign` (Codeer.LowCode.Blazor.Extras) を実装すると、差分に出ず「この版に置き換える」でも触らない。
