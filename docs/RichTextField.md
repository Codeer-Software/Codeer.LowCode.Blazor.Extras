# RichTextField - リッチテキストエディタ

書式付きテキスト (HTML) を編集・保存できる値フィールドです。ツールバーから太字・色・リンクなどの書式を適用できます。

![RichTextField サンプル画面](images/richtext.png)

## 機能

- **書式ツールバー**: 太字、斜体、下線、取り消し線
- **見出し設定**: 標準テキスト / H1〜H6 の見出しレベル
- **リスト**: 箇条書きリスト、番号付きリスト
- **テキスト配置**: 左揃え、中央揃え、右揃え
- **文字色 / 背景色**: 16色パレットから選択
- **リンク挿入**: URL指定でハイパーリンクを挿入
- **書式クリア / Undo / Redo**
- **HTML形式で保存**: DBカラムにHTMLテキストとして永続化

## デザイナー設定プロパティ

「デザイナ表示名」は Designer (日本語環境) で表示されるラベルです。

| プロパティ | デザイナ表示名 | 型 | 説明 |
|---|---|---|---|
| DisplayName | 表示名 | string | フィールドの表示名 (`ValueFieldDesignBase` 継承) |
| DbColumn | DBカラム | string | データを保存するDBカラム名 |
| IsRequired | 必須 | bool | true で未入力をバリデーションエラー (`ValueFieldDesignBase` 継承) |
| OnDataChanged | データ変更イベント | string | データ変更時に呼び出すスクリプトイベント (`ValueFieldDesignBase` 継承) |
| EnableMention | メンション | bool | true で `@` によるメンションを使えるようにする。既定 false (下の「メンション」) |
| MentionListField | メンションの候補の一覧 | string | メンションの候補の行を持つ一覧フィールド (同じモジュールの ListField) の名前 (下の「メンション」) |
| MentionDisplayNameField | 候補の表示名の項目 | string | 一覧の行のうち、候補の表示名として出す項目 |
| MentionLoginNameField | 候補のログイン ID の項目 | string | 一覧の行のうち、ログイン ID として補助に出す項目。空なら出さない |

## 必要なDB構成

HTML文字列を格納するためのテキスト型カラムが必要です。長文を想定する場合は `NVARCHAR(MAX)` や `TEXT` 型を推奨します。

## 表示モード

- **編集モード**: ツールバー付きのエディタを表示。テキストの書式設定が可能
- **閲覧モード**: HTMLをレンダリングして表示。リンクは新しいタブで開く
- **HTML の消毒**: 表示するとき・エディタに入れるとき・貼り付けるときに、ブラウザで HTML を消毒する ([DOMPurify](https://github.com/cure53/DOMPurify))。スクリプトが動くもの (script・イベント属性・javascript: の URL)・フォームの部品・class・位置や重なりを変える style (position・z-index 等) を落とす。文字の書式・色・揃え・表・画像・リンクは残る

## スクリプトAPI

| メンバー | 種別 | 説明 |
|---|---|---|
| Value | プロパティ | HTML文字列値の取得・設定 |
| MentionedIds | プロパティ (string[]) | 今の値に入っているメンションのユーザー Id (読み取りのみ。下の「メンション」) |
| MentionsAll | プロパティ (bool) | 今の値に「全員」のメンションが入っているか (読み取りのみ) |

## メンション

本文の中で `@` を打つと候補が出て、選んだ人を本文に埋め込めます (Slack / Teams のメンションと同じ操作)。「全員」も選べます。範囲は「本文に人を埋め込む」までで、通知とメンションの記録はありません。

候補は、同じモジュールに置いた一覧フィールド (ListField) の行です。誰が候補になるかは、その一覧の検索条件と、一覧が読むモジュールの権限で、設計者が決めます。メンション専用のサーバーの処理はありません。

**この節は 2026-11-24 に決めた仕様です。実装はまだ前の方式 (サーバーの `MentionApi` がユーザーのモジュールをシステムの権限で読む) のままです。** 前の方式との違いは、下の「前の方式から変わる点」にまとめています。

| 段階 | 内容 | 状態 |
|---|---|---|
| 段階 1 | 本文に人を埋め込む (入力の操作・保存する形・閲覧・消毒・スクリプト) | 実装済み |
| 段階 2・3 (置き換え) | 候補を一覧フィールドの行にする (この節の仕様) | 未実装 (前の方式の実装を置き換える) |
| 段階 4 | 通知とメンションの記録 | 未着手 |

### 設定

| プロパティ | デザイナ表示名 | 型 | 説明 |
|---|---|---|---|
| EnableMention | メンション | bool | true で `@` によるメンションを使えるようにする。既定 false (今のアプリの動きを変えない) |
| MentionListField | メンションの候補の一覧 | string | 候補の行を持つ一覧フィールド (同じモジュールの ListField) の名前 |
| MentionDisplayNameField | 候補の表示名の項目 | string | 一覧の行のうち、表示名として出す項目 (TextField) |
| MentionLoginNameField | 候補のログイン ID の項目 | string | 一覧の行のうち、ログイン ID として補助に出す項目 (TextField)。空なら出さない |

ホストの結線は要りません (サーバーの API を使わないため)。

### 一覧の置き方

1. RichTextField と同じモジュールに ListField を置く。
2. 一覧の検索条件のモジュールに、ユーザーのモジュール (`AppSettings.CurrentUserModuleDesignName`) か、一般向けのユーザーモジュール (下の「一覧が読むモジュール」) を指定する。
3. 一覧の検索条件に、候補を絞る条件を書く (同じ部署の人だけ、このプロジェクトのメンバーだけ、有効な人だけ、など)。編集中のレコードの値も `CurrentUser.〜` も、一覧の検索条件でふつうに書ける。
4. 一覧のレイアウトに、表示名の項目 (とログイン ID の項目) を置く。一覧はレイアウトに置いた項目だけを読むため。
5. 一覧は全部の行を持つ設定にする。件数の上限を付けないか、メモリ内ページング (`IsInMemoryPaging`) にする。
6. 一覧は行を編集できない設定にする (行の追加・更新・削除なし)。
7. RichTextField の `MentionListField` にその一覧を、`MentionDisplayNameField` に表示名の項目を指定する。

一覧の並び順が、候補の並び順になります。

### 候補になる人

一覧が持っている行です。つまり次で決まります。

- 一覧の検索条件 (設計者が書く絞り込み)
- 一覧が読むモジュールの権限 (`@` を打っている人の権限での通常の一覧読み。閲覧条件・データの閲覧条件・論理削除・項目の読み取り権限が、ほかの一覧と同じに効く)

RichTextField は、一覧が読んだ行 (`ListField.Rows`) をそのまま使います。メンションのために読み直しはしません。一覧を読み直せば (検索・`Reload`)、候補も変わります。

サーバーが自動で外す人はいません。次は設計者が一覧の検索条件か、一覧が読むモジュールの閲覧条件に書きます。

- 停止中の人 (ログインアカウント契約の有効フラグが偽) を外す
- アプリアクセス条件を満たさない人を外す

候補に出た人が、このフィールドを見られるとは限りません (その人の権限は判定しない)。メンションは本文に入れるだけで誰にも何も送らないので、ここで割り切ります。通知を作る段階 4 でどう扱うかは未定です。

自分自身も、一覧に行があれば候補に出ます。

### 一覧が読むモジュール

ユーザーのモジュールを一般の利用者が読める設計なら、一覧はユーザーのモジュールを読めば足ります。

ユーザーのモジュールを管理者だけが読める設計では、一般の利用者には候補が出ません。その場合は、ユーザーの表を見る**一般向けのユーザーモジュール**を別に作り、一覧にはそれを読ませます。誰に誰が見えるかは、そのモジュールの閲覧条件と、置く項目 (表示名・部署など、利用者に見せてよいものだけ) で決めます。

一般向けのユーザーモジュールに守ってもらう条件は次の 3 つです。設計チェックが指摘します。

- ユーザーのモジュールと同じデータソース・同じ表・同じ Id の列にする (本文に埋める `data-mention-id` がユーザーの Id であるため)。
- 書き込めない設計にする (作成・更新・削除を不可に。ユーザーの表に書けるモジュールが増えると権限の穴になる)。
- ユーザーのモジュールが論理削除の設計なら、同じ論理削除の設定を置く (置かないと、削除済みの人が候補に出る)。

### 件数の制約

候補は、画面を開いたときに一覧が全員分を読みます。**候補は 500 人程度までを目安に設計してください。** これはアプリの設計時の制約です。

- それより多い環境では、一覧の検索条件で絞ります (同じ部署、同じプロジェクトなど)。
- 件数の上限を付けた一覧 (メモリ内ページングでないもの) は、設計チェックが指摘します。上限で切れた先の人が候補に出なくなるためです。
- 一覧のセルの中の RichTextField でメンションを使う形は勧めません。行のモジュールごとに一覧が要り、行数 × 候補の人数を読むことになります。

### 全員

候補の先頭に「全員」(英語環境では「everyone」) を出します。打った文字が表記の先頭と一致するとき (何も打っていないときを含む) だけ出します。「全員」は一覧の行の全員を指しますが、本文に「全員」と埋め込むだけで、誰かに何かを送ることはありません。

### 候補の絞り込みと並び

- 打った文字 (`@` の後ろ) を、表示名の項目とログイン ID の項目に部分一致で当てる (大文字と小文字は区別しない)。当てるのは手元の行で、サーバーには問い合わせない
- 一覧の並びのまま、先頭から 10 件
- 打った文字が 50 文字を超えたら候補は出さない
- 候補の各行は表示名を出す (ログイン ID は補助として小さく出す)。表示名が空の人はログイン ID で出す。どちらも空の行は出さない
- 候補は画面に固定の位置 (`@` の下) に出す。編集欄の枠の下端で切れない
- 一覧がまだ読み終わっていない間は、候補は出ない (読み終わった後に打った文字から出る)

### 入力の操作

- **候補が出る**: 行頭か空白の直後に `@` (全角の `＠` も) を打ったとき。メールアドレスのように文字の直後の `@` では出さない
- **IME**: 変換中は判定しない。確定した後 (`compositionend`) に判定するので、日本語入力のまま `＠やまだ` と打っても候補が出る
- **キー操作**: 候補が出ている間は ↑ / ↓ で選択、Enter か Tab で確定、Esc で閉じる。このとき Enter で改行は入らない。空白を打つか、カーソルを `@` の外へ動かすと候補は閉じる (打った文字はそのまま残る)
- **確定**: `@打った文字` を消して、選んだ人を 1 つの部品として入れ、その後ろに空白を 1 つ入れる
- **部品の扱い**: 部品の途中にカーソルは入らない。Backspace / Delete で部品ごと消える。部品に書式 (太字・色など) を付けることはできる
- **貼り付け**: 別の RichTextField からコピーした部品は部品のまま貼り付けられる (Id も残る)

### 保存する形

部品は HTML の中にこの形で入ります。値は今までどおり HTML の文字列で、DB の列も変わりません。

```html
<!-- 人 -->
<span class="mention" data-mention-id="123">@山田 太郎</span>
<!-- 全員 -->
<span class="mention" data-mention-all="">@全員</span>
```

- `data-mention-id` はユーザーのモジュールの Id の値。どの人かは Id で決まる
- `@山田 太郎` は入れた時点の表示名の写し。あとで表示名を変えても本文は変わらない
- 編集中だけ `contenteditable="false"` を付ける (エディタに入れるときに付け、保存する HTML には残さない)

### 閲覧

- 部品は名前を囲んだチップの見た目で出す (`.mention`。CSS で変えられる)
- 部品をクリックしても何もしない (ユーザーの詳細を開くなどは無い)

### HTML の消毒

消毒 (`safe-html.js` の `richtext`) は class と `data-` 属性を落としますが、メンションの部品の次だけは残します。

- class の `mention` (`data-mention-id` か `data-mention-all` の付いた `span` だけ。リンクなど他の要素に付けた `mention` は落とす)
- 属性の `data-mention-id` と `data-mention-all` (`span` に付いたものだけ)

ほかの class と `data-` 属性は今までどおり落とします。Markdown と AI チャットの表示ではメンションの属性も落とします。

### スクリプト

| メンバー | 種別 | 説明 |
|---|---|---|
| MentionedIds | プロパティ (string[]) | 今の値に入っているメンションのユーザー Id (重複を除き、本文の順) |
| MentionsAll | プロパティ (bool) | 今の値に「全員」が入っているか |

どちらも読み取りだけです。値 (`Value`) の HTML から取り出すので、保存済みかどうかに関係なく今の内容を返します。保存のときのスクリプトから自前の通知を作るといった使い方ができます (Id はブラウザから送られた HTML の中身なので、通知に使うならスクリプト側で実在するユーザーか確かめてください)。

### 権限と監査ログ

- 候補の名前は、`@` を打っている人がもともと見られる行のものだけです。システムの権限で読んだ値は返しません。
- 候補を読むのは一覧の通常の読み込みなので、監査ログにはその一覧の読み出しとして載ります (画面を開いたときと、一覧を読み直したとき。打つたびには載りません)。
- デスクトップ (Wpf / WinForms) でも、一覧が読めればそのまま動きます (差し替えのフックはありません)。

### 設計チェック

どれも `EnableMention` が true のときだけ見ます。メンションはまだ公開していないので、番号は前の方式から振り直しています。

| コード | 内容 |
|---|---|
| RichTextFieldDesign:1 | `MentionListField` が空か、同じモジュールの ListField でない |
| RichTextFieldDesign:2 | 一覧が全部の行を持たない (件数の上限があり、メモリ内ページングでない) |
| RichTextFieldDesign:3 | 一覧が行を編集できる設定になっている |
| RichTextFieldDesign:4 | 一覧が読むモジュールが、ユーザーのモジュールでも、ユーザーのモジュールと同じデータソース・表・Id の列のモジュールでもない (ユーザーのモジュールが無いときを含む) |
| RichTextFieldDesign:5 | `MentionDisplayNameField` が空か、表示名・ログイン ID の項目が一覧の読むモジュールに無いか、一覧のレイアウトに置かれていない |
| RichTextFieldDesign:6 | 一般向けのユーザーモジュールが書き込める (作成・更新・削除のどれかが可) |
| RichTextFieldDesign:7 | ユーザーのモジュールが論理削除なのに、一般向けのユーザーモジュールに同じ論理削除の設定が無い |

一覧と項目の名前の変更 (リファクタ) にも追従します (`ChangeName`)。

### 実装のときに確かめること

仕様を決めた時点 (2026-11-24) で、本体のソースでは確かめていない点です。

- **一覧を画面に見せずに置けるか。** レイアウトに置かない一覧・非表示にした一覧が行を読むかどうか。読まないなら、利用者に見える一覧を置くことになる (その場合は docs にそう書く)。
- **未保存のレコードでの動き。** 編集中のレコードの Id を使う条件 (このプロジェクトのメンバーだけ、など) の一覧は、新規作成の画面では行を読まないはずで、そのとき候補は出ない。確かめて、ここに結果を書く。
- **一覧が読む項目の求め方。** 設計チェック `:5` は「一覧が読む項目」を本体と同じ規則で求める必要がある (本体の一覧にも同じ種類のチェックがある)。
- **500 人を読んだときの画面の重さ。** 一覧は行ごとに Module を作る。

### 前の方式から変わる点

- **サーバーの候補の API を無くす。** `MentionApi` と `MentionCandidateQuery` を削除し、ホストの ExtrasApiTable の `new MentionApi()` の行も要らなくなる。クライアントの `MentionCandidatesCoreAsync` (差し替え) も無くす。
- **`MentionCandidateCondition` を無くす。** 候補の条件は一覧の検索条件に書く。前の方式では書けなかった、編集中のレコードの値を使う条件も書ける。
- **候補は `@` を打っている人が見られる行だけになる。** 前の方式は、ユーザーのモジュールを読めない人にも、システムの権限で読んだ名前とログイン ID を返していた。
- **有効フラグとアプリアクセス条件を、サーバーは判定しなくなる。** 設計者が条件に書く。ログインアカウント契約も使わない (表示名とログイン ID の項目は RichTextField の設計で指定する)。
- **「このフィールドを見られる人」の判定 (前の段階 3) は入れない。** 本体に足した `AuthorizationChecker.CanReadFieldByUser` (本体の `feature/mention`) は、今回は使わない。段階 4 で要るかどうかが決まるまで、本体のブランチは残しておく。
- **打つたびの問い合わせが無くなる。** 待ち時間 (200 ms) も、打つたびの監査ログも無い。

### まだしないこと

- **通知とメンションの記録** (「自分宛てのメンション」の一覧を含む)。段階 4。本文の `data-mention-id` はブラウザが書いた値で、候補に出ていない Id も入れられる。画面の一覧の検索条件もサーバーでは再現できない。宛先をどう確かめるか (実在・有効フラグ・そのフィールドやレコードを読めるか) は段階 4 で決める
- **本文の Id を信用する処理**。ブラウザから送られた HTML は書き換えられるので、表示名と Id が食い違うことがあり得る。メンションは本文の飾りとして扱い、Id で何かをするのは段階 4 でサーバーが確かめてから
- **表示名の変更への追従**。閲覧のたびに今の名前を引き直すと一覧で行ごとの問い合わせが出るため
- **ユーザー以外 (顧客・部署など) のメンション**
- **入れた後に候補から外れた人の扱い**。絞り込みは候補を出すときだけで、本文に入っている部品はそのまま残る
